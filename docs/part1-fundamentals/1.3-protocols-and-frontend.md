## 1.3.1 MQTT：发布订阅模型与 QoS 语义

HTTP 是"请求-响应"：客户端问一句，服务端答一句，不问不答。物联网里这个模型有两个硬伤——设备大部分时间想"说"不想"被问"，而一条服务端状态变化往往要通知很多客户端。MQTT 换成"发布/订阅"：发送方把消息发到某个 Topic（主题），Broker 负责转交给所有订阅者，**收发双方互不知道对方的存在**。

```text
// 图示：demo 的 Topic 树（通配符：+ 匹配单层，# 匹配剩余多层）
iot/
├── gh01/                        ← 产品：温湿度传感器
│   ├── gh01-001/                ← 设备
│   │   ├── up/
│   │   │   ├── telemetry        遥测（QoS 0）
│   │   │   ├── status           状态/档案（QoS 1 + retain）
│   │   │   └── event            告警事件（QoS 1）
│   │   └── down/
│   │       ├── command          控制指令（QoS 1）
│   │       └── command_reply    指令回执（QoS 1）
│   ├── gh01-002/ …  gh01-006/ …
└── pl01/                        ← 产品：智能插座
    ├── pl01-001/ …  pl01-002/ …

前端订阅清单（topics.ts 的 SUBSCRIBE_TOPICS）：
  iot/+/+/up/#                   → 8 台设备的全部上行报文
  iot/+/+/down/command_reply     → 自己所发指令的回执
```

**QoS（服务质量）等级**是 MQTT 最值得前端吃透的概念，它回答"这条消息允不允许丢、允不允许重"：

| QoS | 语义 | 机制 | 开销 | 典型用途 |
| --- | --- | --- | --- | --- |
| 0 | 至多一次（可丢） | 发出即忘，无确认 | 最低 | 高频遥测：丢一条，下一条马上来 |
| 1 | 至少一次（可重） | PUBLISH→PUBACK，超时重发，可能重复 | 中 | 指令、状态、事件：宁重勿丢，重复由业务去重 |
| 2 | 恰好一次 | 四步握手（PUBREC/PUBREL/PUBCOMP） | 最高 | 极少数绝不允许重复且不允许丢失的指令 |

```text
// 图示：三种 QoS 的报文交互（↑=发布方发出，↓=接收方应答）
QoS 0（至多一次）          QoS 1（至少一次）             QoS 2（恰好一次）
发布方          接收方     发布方          接收方         发布方          接收方
  │──PUBLISH───▶│           │──PUBLISH───▶│              │──PUBLISH───▶│
  │             │           │◀──PUBACK────│              │◀──PUBREC────│
  │  （完事）    │           │ 超时未确认→重发│             │───PUBREL───▶│
  ▼             ▼           ▼              ▼              │◀──PUBCOMP───│
                          可能重复！                      四次往返，开销最高
```

demo 的选择是教科书式的：`up/telemetry` 走 QoS 0（高频、容忍丢失），`up/status`、`up/event`、`down/command`、`down/command_reply` 全走 QoS 1（可靠性要紧），重复问题交给业务层——codec 按报文 `mid` 去重。没有一处用 QoS 2，这正是绝大多数系统的真实选择。

MQTT 还有三个弱网场景的关键语义，demo 全都用上了：

- **保留消息（retain）**：Broker 为每个 Topic 保存最后一条 retain 报文，新订阅者订阅瞬间即可收到。设备档案 status 带 retain（见 [simulator.mjs](../../demo/server/simulator.mjs)），所以页面一打开，8 台设备的清单立刻齐了——不用等下一轮上报。
- **遗嘱（LWT）**：客户端连接时预注册一条"遗嘱消息"，若它异常掉线（TCP 断开而未来得及发 DISCONNECT），Broker 代为发布。模拟设备的遗嘱是 `status = { online: false, reason: 'connection_lost' }`——设备拔电，前端秒知离线。
- **会话（clean）**：`clean: true` 表示 Broker 不为客户端保留会话与订阅，断线期间的 QoS 1 消息不补发，重连后须重新订阅（demo 在每次连接成功后显式 subscribe，见 [connection.ts](../../demo/src/services/mqtt/connection.ts)）。`clean: false` 配合 QoS 1 可做离线消息补偿，但会话状态依赖 Broker，行为更难预期。

为什么 MQTT 能成为物联网事实标准？报文头最小只有 2 字节（HTTP 头动辄几百字节）、发布订阅天然解耦海量设备与海量消费者、QoS/retain/LWT 对弱网的一整套语义、以及从开源 Broker 到云平台的完整生态。对前端来说还有一个现实原因：`mqtt.js` 让浏览器端接入几乎没有学习成本——下一节就讲这件事。

## 1.3.2 MQTT over WebSocket：浏览器唯一可行的 MQTT 通道

浏览器出于安全模型，**没有原生 TCP socket**——`WebSocket` 是浏览器里唯一的全双工长连接。于是浏览器接入 MQTT 只有一条路：把 MQTT 报文装进 WebSocket 帧里传输，即 **MQTT over WebSocket**。这是 MQTT 标准的一部分：握手时声明子协议 `mqtt`（`Sec-WebSocket-Protocol: mqtt`），之后帧里跑的就是标准 MQTT 二进制报文。

`mqtt.js` 对此完全透明：根据 URL 前缀自动选择通道——`ws://`/`wss://` 走 WebSocket（浏览器可用），`mqtt://`/`mqtts://` 走 TCP（仅 Node.js 等原生环境可用）。demo 前端的地址在 [demo/.env.development](../../demo/.env.development)：

```text
// 文件: demo/.env.development
VITE_MQTT_URL=ws://localhost:8083/mqtt
```

> 运行方式：该地址随 `pnpm dev` 注入前端（Vite 环境变量），浏览器里由 `mqtt.connect(CONFIG.mqttUrl, …)` 使用。

Broker 端则是一个双入口设计（[broker.mjs](../../demo/server/broker.mjs)）：

```js
// 文件: demo/server/broker.mjs（节选）
// 同一个 aedes 实例的两个入口：设备侧走 TCP，浏览器侧走 WebSocket
const aedes = await Aedes.createBroker()

createTcpServer(aedes.handle).listen(1883)   // 设备侧：MQTT over TCP

const httpServer = createHttpServer()
// websocket-stream 把 WebSocket 包装成 aedes 需要的 duplex 流；路径 /mqtt 是本例约定
websocketStream.createServer({ server: httpServer, path: '/mqtt' }, aedes.handle)
httpServer.listen(8083)                      // 前端侧：MQTT over WebSocket
```

> 运行方式：随终端 1 的 `pnpm server` 启动（或单独 `pnpm broker`），就绪后打印 `TCP 已就绪` 与 `WS 已就绪` 两行日志。

```text
// 图示：双入口 Broker——设备与前端汇入同一个消息枢纽
 8 台模拟设备                        浏览器监控台
 (simulator.mjs)                    (mqtt.js)
      │ 原生 MQTT                        │ MQTT over WebSocket
      ▼                                  ▼
 ┌──────────────┐              ┌─────────────────────┐
 │  设备侧入口   │── TCP 1883 ─▶│                     │
 └──────────────┘              │       aedes         │  两个入口汇入同一个
                               │      .handle        │  Broker 实例，
 ┌──────────────┐              │                     │  Topic 路由完全一致
 │  前端侧入口   │─ WS 8083 ───▶│                     │
 └──────────────┘  path /mqtt  └─────────────────────┘
```

前端连接代码的关键参数都有讲究：

```ts
// 文件: demo/src/services/mqtt/connection.ts（节选）
this.client = mqtt.connect(CONFIG.mqttUrl, {
  // 同 clientId 的两个连接会互踢：加随机后缀，避免多标签页互相挤下线
  clientId: `${CONFIG.clientIdPrefix}_${Math.random().toString(36).slice(2, 10)}`,
  clean: true,          // 不依赖 Broker 保留会话；重连成功后显式重订阅
  keepalive: 30,        // 30s 心跳；Broker 超时未收到心跳即判定客户端掉线（触发遗嘱）
  reconnectPeriod: 0,   // 关闭 mqtt.js 内置重连，改由自研"全抖动指数退避"接管
  connectTimeout: 8_000,
})
```

> 运行方式：随 demo 前端运行（终端 1 `pnpm server`，终端 2 `pnpm dev`），效果在本节末尾的"运行与验证"中逐帧观察。

连接建立后还有两件事：订阅与消息接收——它们正是 DevTools 里 SUBSCRIBE/SUBACK/PUBLISH 帧的来源：

```ts
// 文件: demo/src/services/mqtt/connection.ts（节选）
this.client.on('connect', () => {
  this.setState('connected')
  // clean 会话不保留订阅 → 每次（重）连接成功后必须显式重订阅
  this.client?.subscribe([...SUBSCRIBE_TOPICS], { qos: 1 }, (err) => {
    if (err) console.error('[mqtt] 订阅失败', err)
  })
})

this.client.on('message', (topic, payload) => {
  // 每条入站 PUBLISH 帧都会触发一次，交给上层路由（第 1.1 章上行链路的第⑤步）
  this.events.onMessage(topic, payload)
})
```

> 运行方式：随 demo 前端运行；DevTools 的 WS 面板里，subscribe 对应可见的 SUBSCRIBE/SUBACK 帧对，之后每个 message 回调对应一条入站 PUBLISH 帧。

连接的整个生命周期由一个五态状态机管理（`ConnState`：idle/connecting/connected/reconnecting/closed，UI 侧由连接指示器实时展示）：

```text
// 图示：MqttConnection 状态机（connection.ts）
         connect()             on('connect')
 idle ────────────▶ connecting ─────────────▶ connected
                        │                      │  30s keepalive 心跳保活
                        │ 8s 超时 / on('close')  │  90s 无任何入站报文 → 判定"假死"
                        ▼                      ▼
                   reconnecting ◀───────────────┘
                        │  全抖动指数退避：delay = random(0, min(30s, 1s × 2^attempt))
                        └─▶ connect()（attempt+1，直至成功；随机化避免重连风暴）
任何状态调用 end() ──▶ closed（不再重连）
```

## 1.3.3 其余三种协议：CoAP、原生 WebSocket、HTTP

**CoAP**（Constrained Application Protocol）为资源极度受限的设备而生：跑在 UDP 上，报文头只有 4 字节起，配 DTLS 加密；模型是请求/响应，但提供 **Observe 模式**——客户端注册观察某个资源后，服务端主动推送其变化，效果类似订阅。电池要用数年的 NB-IoT 水表气表是它的主场。关键结论：**浏览器无法直连 CoAP**（浏览器没有 UDP socket），设备数据必须经网关或平台转成 MQTT/HTTP，前端再从转换结果接入——你在浏览器里永远不会"看见"CoAP，但要知道上游存在这一层。

**原生 WebSocket 直连**：全双工、延迟低，但 MQTT 的 QoS/retain/LWT/会话语义一概没有，全要自建——心跳保活、指数退避重连、自定义序列化与消息序号、断线补偿、重复去重。本仓库的姊妹教程《React 19 + WebSocket 实战》完整示范过这套做法：应用层心跳包 + 退避重连 + JSON 协议 + 序列号去重。结论是可行但贵：每接一类业务就要重造一遍可靠性设施。适合没有 MQTT 基础设施、或消息语义简单的场景（聊天室、行情推送、协同编辑）。

**HTTP**：请求/响应、无状态、连接开销大、服务端无法主动推。设备高频上行用它既费电又费流量，但它在两个场景无可替代：**OTA 固件下载**（大文件、断点续传、CDN 分发）与**配置/证书拉取**（设备注册、一机一密激活）。前端侧同理——即使实时通道走 MQTT，历史数据查询、设备列表分页通常还是 HTTP（第 1.2 章的路径 A 与路径 B 混合模式）。

## 1.3.4 五协议对比与前端选型决策树

| 维度 | MQTT（TCP） | MQTT over WebSocket | CoAP | 原生 WebSocket | HTTP |
| --- | --- | --- | --- | --- | --- |
| 传输层 | TCP/TLS | WebSocket（TCP） | UDP/DTLS | TCP/TLS | TCP/TLS |
| 模型 | 发布/订阅 | 发布/订阅 | 请求/响应 + Observe | 全双工消息帧 | 请求/响应 |
| 浏览器直连 | 否（无原生 TCP） | 是（mqtt.js） | 否（无原生 UDP） | 是（原生） | 是（原生） |
| QoS/retain/遗嘱 | 完整 | 完整（同 MQTT） | 有 QoS 0/1，无 retain/LWT | 无，需自建 | 无 |
| 功耗与报文开销 | 低（头 2 字节起） | 低（多一层 WS 帧封装） | 极低（头 4 字节起） | 中 | 高（头大、频繁建连） |
| 典型场景 | 设备侧接入 | Web 监控台/大屏 | NB-IoT 表计等受限设备 | 自定义实时通道 | OTA、配置拉取、报表 |

```text
// 图示：前端协议选型决策树（从"接入方是谁"出发）
接入方是浏览器吗？
├─ 否（App / 小程序 / 设备固件 / 边缘网关）
│    ├─ 资源极度受限、电池供能、窄带（NB-IoT 表计）──▶ CoAP（经网关转 MQTT/HTTP 入云）
│    └─ 一般设备或原生客户端 ────────────────────▶ 原生 MQTT（TCP/TLS，8883）
└─ 是（浏览器，无原生 TCP/UDP）
     ├─ 不需要服务端主动推送，偶发查询即可 ───────▶ HTTP/REST（需要"半实时"再配 SSE）
     ├─ 需要实时推送（甚至双向控制）
     │    ├─ 要 QoS/retain/遗嘱 等 MQTT 语义，
     │    │   且 Broker 有 WS 入口 ────────────▶ MQTT over WebSocket ✅（demo 选它）
     │    ├─ 消息语义简单，愿意自建心跳/重连/去重 ──▶ 原生 WebSocket
     │    └─ 只需要服务端→前端单向推 ─────────────▶ SSE（更轻，无需双向）
     └─ 叠加规则：OTA 固件、大文件、历史报表 ──────▶ 永远走 HTTP，与实时通道并存
```

demo 的完整选型理由：设备侧用原生 MQTT（TCP 1883）模拟真实设备的接入方式；前端浏览器只能走 WS，于是 aedes 挂了 WebSocket 入口（8083 /mqtt）；业务需要双向（订阅遥测 + 下发指令）、需要 retain（开页秒出设备档案）、需要遗嘱（离线即知）、需要 QoS 分级（遥测与指令可靠性不同）——四项需求叠加，MQTT over WebSocket 是唯一同时满足的选择。若你的系统只需要"服务端单向推行情/公告"，原生 WebSocket 或 SSE 反而更简单。

最后记住一点：**协议选型不是终身契约**。demo 的分层（connection / gateway / store 各司其职）保证了一旦未来要把通道换成原生 WebSocket 或平台 API，只有 `MqttConnection` 一层需要重写——把"协议语义"封装在连接层，把"业务语义"留给 store，这是前端应对协议演化的关键设计。

## 最佳实践与常见坑

- **现象**：在浏览器里写 `mqtt.connect('mqtt://localhost:1883')`，连接直接失败。
  **原因**：浏览器没有原生 TCP，`mqtt://` 只能在 Node 等原生环境使用。
  **解法**：浏览器一律用 `ws://host:8083/mqtt` 形态；生产环境页面是 https 时必须用 `wss://`（TLS WebSocket）。

- **现象**：https 部署后前端连不上 Broker，控制台报 Mixed Content 错误。
  **原因**：安全页面（https）禁止发起不加密的 `ws://` 连接，这是浏览器混合内容策略。
  **解法**：Broker 挂 TLS 证书提供 `wss://` 入口，`.env.production` 中的地址同步改为 wss 并走域名与标准端口。

- **现象**：觉得"QoS 2 最可靠"，把所有 Topic 都升到 QoS 2，结果吞吐骤降。
  **原因**：QoS 2 的四步握手让每条消息的网络往返翻倍，Broker 负担剧增，部分设备端实现也不完整。
  **解法**：按语义分级——遥测 QoS 0，状态/事件/指令 QoS 1，重复问题交给业务去重（demo 按报文 `mid` 去重）；QoS 2 只留给绝不允许重复的极少数指令。

- **现象**：DevTools 的 WS Messages 全是乱码，怀疑有 bug。
  **原因**：MQTT over WebSocket 的载荷是 MQTT 二进制报文，浏览器不认识 MQTT 语义，只显示字节。
  **解法**：观察帧的↑↓方向、长度与时序即可定位大半问题；精确调试用 `mqtt.js` 的事件回调（`on('message')` 打印 topic/payload），或对照终端 1 的报文日志。

- **现象**：弱网下页面频繁提示重连；或掉线后很久才被发现。
  **原因**：keepalive 设得太小，网络抖动就会被误判掉线；设得太大则离线感知迟钝。而且 TCP"假死"（连接还在、数据不通）是心跳感知不到的。
  **解法**：keepalive 30 秒是常见折中；再加一层入站看门狗兜底——demo 在 90 秒收不到任何报文时主动断开重连（connection.ts 的 `INBOUND_WATCHDOG_MS`）。
