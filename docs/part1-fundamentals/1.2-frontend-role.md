## 1.2.1 前端的四大职责

在物联网系统里，前端是"物"与"人"之间唯一的翻译官。它的四大职责各自挂在数据链路的不同位置：

```text
// 图示：四大职责与上行/下行链路的对应关系
                 ┌────────────── ① 数据可视化（消费上行）──────────────┐
 遥测 up/*  ────▶│  设备卡片 / ECharts 实时曲线                        │
 告警 up/event ─▶│  ③ 告警处置：告警中心 / 横幅 / 未读徽标（消费上行）   │
                 └────────────────────────────────────────────────────┘
                 ┌────────────── ② 控制指令入口（发起下行）────────────┐
 人的操作  ─────▶│  远程控制面板：开关 / 设阈值 / 重启                   │──▶ down/command
                 └────────────────────────────────────────────────────┘
                 ┌────────────── ④ 设备与规则配置（发起下行）──────────┐
 配置项    ─────▶│  阈值下发 setThreshold /（生产中：物模型与规则 UI）   │──▶ down/command
                 └────────────────────────────────────────────────────┘
```

| 职责 | 做什么 | demo 对应 | 关键技术 |
| --- | --- | --- | --- |
| ① 数据可视化 | 把遥测字节流变成可读的曲线、状态、仪表 | 设备卡片列表、详情页 ECharts 实时曲线 | ECharts 增量绘制、滑动窗口、渲染节流 |
| ② 控制指令入口 | 把人的操作变成设备指令，并呈现指令生命周期 | 远程控制面板：开关 / 设阈值 / 重启 | RPC over MQTT、Promise 三态（ok/rejected/timeout） |
| ③ 告警处置 | 把异常事件变成"可处理的待办"而不是刷屏噪音 | 告警中心 + 全局告警横幅 + 侧边栏未读徽标 | 冷却去重、聚合、确认（ack）流 |
| ④ 设备与规则配置 | 维护设备档案、阈值、联动规则等结构化配置 | `setThreshold` 阈值下发（完整配置中心从简） | 表单校验、物模型配置 UI |

①③ 主要消费上行，②④ 主要发起下行——这也决定了各自的技术难点：①③ 难在"高频数据不卡界面"，②④ 难在"不可靠网络下的可靠交互"。控制指令的交互本质是一个三态状态机（还记得 1.1 章的 RPC over MQTT 吗？）：

```text
// 图示：指令生命周期三态（ControlPanel.vue 的 logs 状态机）
点击按钮 ──▶ pending（执行中，按钮禁用防重复点击）
                │
                ├─ 收到回执 ok=true ────────────▶ ok       如「开关已打开」
                ├─ 收到回执 ok=false ───────────▶ rejected 如「阈值超出允许范围 [20, 60]」
                └─ 8s 内无回执（commandTimeoutMs）▶ timeout  「8s 内未收到设备回执」
```

除这四类之外，还有三个常见的**扩展方向**，进阶后会遇到：

- **数据大屏**：把 ① 推到极端——几十路曲线同屏轮播，核心变成聚合与降采样策略；
- **数字孪生 3D**：用 Three.js/WebGL 把设备状态映射到三维场景（楼宇、厂区、管线），实时数据绑定在 3D 节点上；
- **边缘网关面板**：为部署在机房/厂区的边缘网关写本地 Web 管理界面（局域网访问、弱依赖云端），是前端离"物"最近的一种岗位。

## 1.2.2 职责边界：前端不做什么

初学者最容易犯的错误，是按"Web 开发"的惯性把前端当成全能层。以下三件事，请明确划出边界：

| 前端不做的事 | 为什么不做 | 谁来做 | demo 的分界 |
| --- | --- | --- | --- |
| 不直连设备的 TCP/UDP | 浏览器没有原生 TCP socket；出于沙箱与混合内容安全模型也不允许。设备侧的 TCP/TLS 接入只能由设备 SDK 或网关完成 | 设备 SDK / 边缘网关 | 设备走 TCP 1883，前端只能走 WebSocket 8083 |
| 不承担协议编解码的最终责任 | 报文契约是设备与平台之间的协议；前端只做"展示前校验"，发现坏数据丢弃即可，没有资格也没有能力"修正"契约 | 平台 / 设备固件 | [codec.ts](../../demo/src/services/mqtt/codec.ts) 把解码收敛为一层：校验、按 `mid` 去重、时钟纠偏（漂移超 5 分钟钳制为本地时间），UI 层零容错代码 |
| 不做海量数据存储与规则引擎 | 时序数据的存储、降采样、跨设备联动计算，量级远超浏览器内存与生命周期；"温度超 35℃ 告警"这类规则若在前端跑，页面一关规则就消失 | 时序数据库 / 平台规则引擎 | 前端只保留 `windowCap = 120` 点的滑动窗口（[config.ts](../../demo/src/config.ts)）；告警三条来源中，平台规则引擎那一路 demo 未启用 |

一句话总结边界：**前端负责"人与物的界面"，不负责"物与物的基础设施"**。浏览器的能力边界（无原生 TCP、内存有限、生命周期随页面）决定了这些事做不了；安全边界（不持有设备密钥、不经手原始遥测的最终存储）决定了这些事不该做。

"不做"不是"不存"。前端照样要在内存里维护一份近期数据供界面消费——关键是它必须是**有界的**。看 demo 滑动窗口的裁剪逻辑：

```ts
// 文件: demo/src/stores/devices.ts（节选）
// 遥测入库：只保留最近 windowCap=120 个点，防止长会话内存无限增长
for (const p of points) e.window.push(p)
if (e.window.length > CONFIG.windowCap) {
  e.window.splice(0, e.window.length - CONFIG.windowCap) // 一次性裁掉最旧的多余点
}
```

> 运行方式：以上逻辑随 demo 前端运行（终端 1 `pnpm server`，终端 2 `pnpm dev`），把页面开着看一天，内存占用也不会随消息数线性增长。

另一条边界——"不承担协议编解码的最终责任"——在 demo 里落地为一个独立的解码层，坏数据在这里被拦下：

```ts
// 文件: demo/src/services/mqtt/codec.ts（节选）
// Result 风格返回值：调用方无需 try/catch，坏报文在这里被拦下
export type DecodeResult<T> = { ok: true; value: T } | { ok: false; reason: string }

// 数值清洗：字符串数字兜底转换，其余非有限数一律剔除，绝不让 NaN 流进图表
function num(v: unknown): number | undefined {
  if (typeof v === 'number' && Number.isFinite(v)) return v
  if (typeof v === 'string' && v.trim() !== '' && Number.isFinite(Number(v))) return Number(v)
  return undefined
}
```

> 运行方式：随 demo 前端运行；它的统计结果（收到/解码/丢弃/重复/纠时五个计数）显示在侧边栏连接指示器的底部，联调时盯着它就知道链路上有多少"脏数据"被拦。

注意"不做"不等于"不了解"。前端必须理解 Broker 的转发语义、Topic 契约和 QoS 含义，才能设计出正确的界面状态（比如 1.1 章的指令三态）。你划出去的是实现，不是知识。

最后用一张"Web 直觉 vs IoT 实际"对照表收尾，这几条误区几乎每个转行做 IoT 前端的人都踩过：

| Web 开发直觉 | IoT 实际 | demo 的做法 |
| --- | --- | --- |
| "数据丢了就重拉一次接口" | 设备上报是推流，没有"重拉"；丢包靠 QoS 与补发语义兜底 | 遥测 QoS 0 丢了就丢了，下一条 4~8 秒内就来 |
| "接口报错要 toast 提醒用户" | 每秒多条消息，逐条弹窗等于拒绝服务 | 坏报文静默丢弃，计数累加在连接指示器里 |
| "状态存组件里就行" | 消息流按设备 id 高频写入，且要跨页面共享 | Pinia store 以 `Record<deviceId, Entry>` 收敛 |
| "轮询一下最简单" | 高频遥测下轮询既慢又贵，还拿不到下行能力 | 实时通道走 MQTT over WebSocket（第 1.3 章） |

## 1.2.3 两条接入路径：经平台 API vs 直连 Broker

确定职责后，下一个决策是：前端的实时数据从哪里来？两条主流路径：

```text
// 图示：前端接入设备的两条路径
路径 A：经平台 API（拉取 + 推送）
  设备 ── MQTT ──▶ 云平台 ──┬── REST/GraphQL（前端轮询，秒~分钟级）
                            └── SSE/长轮询（服务端单向推，秒级）
                            ────▶ 前端

路径 B：前端直连 Broker（demo 采用）
  设备 ── MQTT(TCP 1883) ──▶ Broker ── MQTT over WebSocket(8083) ──▶ mqtt.js ──▶ 前端
                 （平台职责被 aedes 简化：只剩按 Topic 转发）
```

| 维度 | 路径 A：平台 API（轮询/SSE） | 路径 B：直连 Broker（MQTT over WebSocket） |
| --- | --- | --- |
| 实时性 | 轮询秒~分钟级；SSE 秒级 | 推送，毫秒~秒级 |
| 通信方向 | 请求-响应；SSE 单向 | 全双工（可上行可下行） |
| 鉴权 | 成熟：API 网关、Cookie/JWT 统一管 | Broker 凭证需平台另行签发短时 token |
| 订阅粒度 | 按 API 资源，一次拿一批 | Topic 级，可用通配符精细订阅 |
| 历史数据/快照 | 天然擅长（查询接口） | Broker 不存历史；demo 靠 retain 消息部分弥补 |
| 服务端成本 | 高频轮询压力大 | 消息压力在 Broker，API 侧轻 |
| 浏览器适配 | 原生支持 | 需 Broker 开 WS 入口（见第 1.3 章） |
| 典型场景 | 管理后台、报表页、城市级海量设备 | 监控台、实时大屏、设备数可控的园区级系统 |

demo 选择路径 B，理由有三：其一，8 台设备全量订阅毫无压力，Topic 通配符 `iot/+/+/up/#` 一句话收齐上行；其二，双向是刚需——控制指令要从同一条连接发下去；其三，教学上最能暴露 MQTT 的真实语义（QoS/retain/LWT 全都亲历）。

生产系统最常见的是**混合模式**：历史曲线、设备列表分页走 REST（快照），实时增量走 MQTT over WebSocket（推流），互为补位。demo 里 retain 的 status 消息在订阅瞬间回放设备档案，相当于 Broker 替你做了半个"快照接口"；而完整的时序历史，demo 用 120 点滑动窗口代替——这两个取舍你要能讲清楚。

选路径 B 时有一件事必须由平台侧配套：**凭证签发**。浏览器不应持有设备的 MQTT 用户名密码，正确做法是前端先向平台 API 换取短时 token，再凭它连接 Broker；demo 为了教学简化，本地 Broker 完全开放（无鉴权），这一点在生产环境不可照搬。

前端怎么接入这条链路？demo 用了一个"装配层"把无框架依赖的服务层接进 Pinia：

```ts
// 文件: demo/src/composables/useIot.ts（节选）
// 网关不 import 任何 store——依赖全部通过回调注入，服务层保持可单测
const gateway = new IotGateway({
  onConnectionState: (state, attempt, detail) => conn.set(state, attempt, detail),
  onProfile: (deviceId, productId, s) => devices.ingestProfile(deviceId, productId, s),
  onTelemetry: (deviceId, productId, points) => devices.ingestTelemetry(deviceId, productId, points),
  onEvent: (deviceId, productId, ev) => alerts.pushEvent(deviceId, devices.nameOf(deviceId, productId), ev),
})
gateway.start()
devices.startWatchdog() // 前端离线看门狗：兜底 status 报文丢失等"静默故障"
```

> 运行方式：装配逻辑在 `App.vue` 的 `onMounted` 中随页面启动（[App.vue](../../demo/src/App.vue)），整个应用生命周期只有一条 MQTT 连接。

留意最后一句 `devices.startWatchdog()`：它兜底一切"静默故障"——设备半死不活但 TCP 连接还在时，遗嘱不会触发，靠 `lastSeenAt` 超时推导离线（详见 [stores/devices.ts](../../demo/src/stores/devices.ts)）。

## 运行与验证

跑起 demo，亲手把界面与四大职责对上号：

```shell
# 文件: iot-tutorial-project/demo/（两个终端分别执行）
pnpm server     # 终端 1：Broker + 8 台模拟设备
pnpm dev        # 终端 2：监控台（5173，被占用则顺延 5174）
```

> 运行方式：`cd iot-tutorial-project/demo` 后执行；浏览器打开终端 2 输出的地址（如 http://localhost:5173）。

按下面的顺序操作，每一步都对应一个职责：

1. **① 可视化**：进入"设备列表"，应看到 8 台设备卡片秒出（retain 回放档案）；点进 `gh01-001`，曲线每 4~8 秒向右生长一个点。
2. **② 控制**：进入 `pl01-001`（智能插座）详情页，点"开关"按钮——按钮变为"执行中"（pending），约 300ms 后日志区变为"成功"（ok），开关状态翻转；随后曲线上的功率归零或回升。
3. **③ 告警**：等 `gh01-003` 偶发温度尖峰，侧边栏徽标 +1，顶部弹出告警横幅；进入"告警中心"点"全部确认"，徽标清零。
4. **④ 配置**：在 `gh01-001` 详情页把温度阈值改为 25（合法范围 [20, 60]），观察指令日志回执"温度阈值已更新为 25℃"；再尝试改成 80，应看到"被拒绝"（rejected）。
5. **离线剧本**：回到列表页静候，约 40 秒后 `gh01-006` 计划内下线，应弹出 warn 级"设备离线（graceful_shutdown）"。
6. **连接可视化**：全程观察侧边栏底部的连接指示器——连接五态的切换，以及"收到/解码/丢弃/重复/纠时"五个解码计数的变化（重复计数增长，说明设备在重发脏报文，见 1.2.2 的解码层）。

## 最佳实践与常见坑

- **现象**：指令点了没反应，用户连点五次，设备收到五条重复指令。
  **原因**：指令回执有真实时延（demo 里是 300ms 模拟，真机可能数秒），界面若不呈现"执行中"状态，用户必然重试。
  **解法**：按钮点击即进入 pending 并禁用，以回执 id 关联 Promise（[ControlPanel.vue](../../demo/src/components/ControlPanel.vue) 的 `logs` 数组），ok/rejected/timeout 三态分别给出明确文案；timeout 后允许重试而非自动重发。

- **现象**：监控台开一天后越来越卡，内存持续上涨。
  **原因**：遥测无限堆积进组件状态，且每个点都触发一次全量重绘。
  **解法**：三件套——滑动窗口定长裁剪（`windowCap`）、图表增量 append、渲染节流合并高频帧。把"存多少"收敛在 store 一处，别散在组件里。

- **现象**：开两个浏览器标签页联调，两边互相提示掉线。
  **原因**：MQTT 规定同一 clientId 的两个连接互踢；若 clientId 写死，两个标签页就成了"同一个客户端"。
  **解法**：clientId 加随机后缀（demo：`web-console_xxxxxxxx`，见 [connection.ts](../../demo/src/services/mqtt/connection.ts)）；同时意识到每个标签页一条连接的规模隐患，必要时改用服务端汇聚后经 SSE 广播。

- **现象**：设备断网瞬间告警中心被刷屏，恢复后又来一波。
  **原因**：把每次"错过上报"都当成离线事件告警，且没有去重窗口。
  **解法**：同设备同 code 在冷却窗口内只收第一条（demo 为 60 秒，见 [stores/alerts.ts](../../demo/src/stores/alerts.ts)）；离线告警用 `offlineAlerted` 标志保证一次离线只报一次；列表设容量上限（demo 200 条）防长会话膨胀。

- **现象**：曲线上偶现"回跳"的旧点，或温度突然跳回几分钟前。
  **原因**：demo 特意制造的脏数据剧本——约 6% 概率原样重发上一条遥测（`mid` 相同），低功耗批量样本带约 90 秒的设备时钟偏移。
  **解法**：解码层按 `mid` 去重；时间戳漂移超过阈值就钳制为本地接收时间（见 codec.ts）。容错收敛在解码层一处，曲线永远单调向前，UI 层不用写一行补丁。
