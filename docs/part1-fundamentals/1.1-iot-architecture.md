## 学习目标

- 说出物联网四层架构中每一层的职责，并各举出一个代表技术；
- 用 ASCII 图画出一条遥测数据从设备到 ECharts 曲线的完整上行链路，以及一条控制指令的完整下行链路；

- 对比公有云 IoT 平台与自建 Broker 的取舍，按规模分级估算前端将要面对的消息量。

## 1.1.1 四层架构与关键角色：数据从哪里来，到哪里去

物联网系统无论多复杂，都可以拆成四层。先看总览（右侧标注了每一层在配套 demo 中的对应物）：

```text
// 图示：物联网四层架构与 demo 的对应关系
┌──────────────────────────────────────────────────────────────────┐
│ 应用层   Web 监控台 / 移动 App / 大屏 / 业务系统                    │
│          demo：Vue3 + Pinia + ECharts 设备监控台（demo/src）       │
├─────────────────────────────↑↓───────────────────────────────────┤
│ 平台层   Broker / 设备管理 / 规则引擎 / 时序数据库 / 设备影子        │
│          demo：aedes 内存 Broker（demo/server/broker.mjs）         │
├─────────────────────────────↑↓───────────────────────────────────┤
│ 网络层   TCP/TLS、WebSocket、Wi-Fi、蓝牙、LoRa、NB-IoT、4G/5G，    │
│          以及其上的 MQTT / CoAP / HTTP 等应用协议                   │
│          demo：TCP 1883（设备侧）+ WebSocket 8083（前端侧）         │
├─────────────────────────────↑↓───────────────────────────────────┤
│ 感知层   传感器 / MCU / 摄像头 / 执行器——真实世界里的"物"           │
│          demo：8 台模拟设备（demo/server/simulator.mjs）           │
└──────────────────────────────────────────────────────────────────┘
```

注意图中的箭头是双向的：遥测数据上行，控制指令下行。分层不是要你在每一层都写代码，而是给你一张"问题定位地图"——曲线不动了，是感知层没采到、网络层丢了、平台层没转，还是应用层没画？每一层的职责与代表技术：

| 层 | 核心职责 | 代表技术 | demo 对应物 |
| --- | --- | --- | --- |
| 感知层 | 采集物理量（温度、电量、功率），执行动作（开关、阀门） | 温湿度传感器、MCU（ESP32 等）、RFID、摄像头、继电器 | `simulator.mjs` 模拟的 8 台设备 |
| 网络层 | 把数据从受限设备搬进 IP 世界，并选择传输与应用协议 | Wi-Fi、蓝牙 Mesh、LoRa、NB-IoT、以太网；MQTT、CoAP、HTTP | 本机回环：TCP 1883 / WS 8083 |
| 平台层 | 设备接入、消息路由、存储、规则联动、安全管理 | aedes / EMQX / Mosquitto，规则引擎，时序数据库（TDengine 等） | `broker.mjs`（aedes 内存实现） |
| 应用层 | 把数据变成人可用的界面，把人的操作变成指令 | Vue / React + ECharts / Three.js，移动端 | `demo/src` 下的设备监控台 |

接下来是前端读 IoT 文档时的"术语关"。下表左边是概念，右边是它在 demo 里的落点，全部可以在源码中找到：

| 术语 | 一句话定义 | 在 demo 中的落点 |
| --- | --- | --- |
| 设备（Device） | 一台可寻址、有唯一 ID 的物理或虚拟终端 | `simulator.mjs` 中的 8 台设备，id 形如 `gh01-001` |
| 网关（Gateway） | 帮受限网络设备接入 IP 世界的中间节点 | demo 中被简化掉（模拟器自身就是"设备"） |
| Broker（消息枢纽） | MQTT 服务端，按 Topic 转发消息，不存储业务数据 | `broker.mjs`（aedes 内存实现） |
| 规则引擎 | 平台上按条件（Topic/载荷/阈值）触发的服务端逻辑 | demo 未启用；`alerts.ts` 注释保留了平台推送入口 |
| 时序数据库 | 按"时间 + 指标"优化的存储，支持降采样与聚合查询 | demo 无持久化；前端用 120 点滑动窗口替代 |
| 设备影子 | 云端保存的设备最新状态快照，设备与界面各自异步读写 | 保留消息版 status 充当轻量影子 |
| 遥测（Telemetry） | 周期上报的连续量：温度、湿度、功率 | `up/telemetry`，QoS 0 |
| 遥信（Status/离散量） | 离散状态：在线/离线、开关开合 | `up/status` + telemetry 中的 `on` 字段 |
| 遥控（Command） | 下行控制指令：开关、重启、设阈值 | `down/command`（QoS 1） |
| Topic | 消息的"地址"，发布/订阅的路由依据 | `iot/{productId}/{deviceId}/{dir}/{kind}` |
| QoS | 服务质量等级 0/1/2（语义见第 1.3 章） | 遥测用 0，状态/事件/指令用 1 |
| 保留消息（Retain） | Broker 为每个 Topic 保存最后一条 retain 报文，订阅瞬间送达 | 设备档案 status（`retain: true`） |
| 遗嘱（LWT） | 客户端异常掉线时，由 Broker 代发布的预设消息 | `simulator.mjs` 的 `will` 选项，掉线发布 offline |
| clientId | 客户端身份；同 id 的两个连接会互踢 | 设备 `dev-{id}`，前端 `web-console_随机串` |

其中"保留消息 + 遗嘱"这对组合，是前端**打开页面瞬间就能看到完整设备清单**的原因：订阅 `iot/+/+/up/status` 后，Broker 立刻回放每台设备 retain 的档案；设备拔电时遗嘱又会替它广播 offline。这两个语义会在第 1.3 章展开。

## 1.1.2 端-边-云：什么时候需要边缘计算

把四层架构按"算力放在哪"重新折叠，就得到端-边-云三级形态：

- **端（设备侧）**：传感器与 MCU，只做采集和最基础的执行；
- **边（边缘网关/边缘服务器）**：部署在设备附近（同一厂区、同一楼宇）的计算节点，就近处理数据、就近下发控制；
- **云（平台侧）**：集中接入、长期存储、跨地域分析与全局管理。

demo 里没有独立的"边"——模拟设备直连云端 Broker。你可以想象把 `server/` 整个目录搬到一台树莓派上放进大棚，它就是一个最小边缘网关。什么时候值得引入这一层？出现以下任一信号时：

| 信号 | 典型例子 | 边缘节点做什么 |
| --- | --- | --- |
| 时延敏感 | 工业产线急停要求毫秒级响应 | 就近判定，不等云端往返 |
| 断网自治 | 矿井、车载、仓库断外网仍要运转 | 本地缓存遥测 + 本地规则，恢复后再补传 |
| 带宽成本 | 200 路摄像头原始视频回传云端 | 边缘做识别，只回传结构化结果 |
| 数据合规 | 工厂数据不允许出园区 | 原始数据留在本地，云端只收汇总 |

反过来，如果只是几百个温湿度传感器、秒级上报、没有实时控制诉求，"端→云"直连就是最简架构，别为不存在的问题买设备。前端同学尤其要意识到：**边缘计算的引入会改变前端对接的对象**——监控界面可能从"连云平台"变成"连厂区边缘网关的本地 Web 服务"，部署形态、鉴权方式、离线行为都会随之改变。

## 1.1.3 Topic 契约与两条链路

demo 的所有消息都走一套 Topic 契约（定义在 [topics.ts](../../demo/src/services/mqtt/topics.ts)）：

| Topic | 方向 | 内容 | QoS | 保留消息 |
| --- | --- | --- | --- | --- |
| `iot/{productId}/{deviceId}/up/telemetry` | 设备→云 | 温湿度/电量/功率 JSON | 0 | 否 |
| `iot/{productId}/{deviceId}/up/status` | 设备→云 | 在线状态与设备档案 | 1 | 是 |
| `iot/{productId}/{deviceId}/up/event` | 设备→云 | 告警事件（超温、低电） | 1 | 否 |
| `iot/{productId}/{deviceId}/down/command` | 云→设备 | 控制指令 | 1 | 否 |
| `iot/{productId}/{deviceId}/down/command_reply` | 设备→云 | 指令回执 | 1 | 否 |

配合报文样例，把契约落到字节级（载荷均为 JSON 字符串）：

```text
// 文件: demo/server/simulator.mjs —— 各 Topic 的报文样式
up/status            在线档案（QoS1 + retain）
  {"online":true,"name":"育苗棚 A1 · 温湿度","product":{"id":"gh01","name":"温湿度传感器"},"fw":"v1.4.2","ip":"192.168.1.20"}
up/telemetry         普通遥测（QoS0）
  {"mid":"9f2c…","ts":1760700000000,"temp":26.4,"humi":57.2,"battery":86,"rssi":-58}
up/telemetry         低功耗批量（QoS0；samples 含 4 个缓存样本，设备时钟偏移约 +90s）
  {"mid":"31ab…","ts":1760700015000,"samples":[{"t":1760700006000,"temp":26.8,"humi":56.1,"battery":85}, …]}
up/event             告警事件（QoS1）
  {"mid":"77de…","ts":1760700030000,"code":"TEMP_HIGH","level":"error","message":"温度 37.2℃ 超过阈值 35℃","value":37.2}
down/command         前端 → 设备（QoS1；id 用于关联回执）
  {"id":"c0ffee…","action":"switch","params":{"on":false},"issuedAt":1760700060000}
down/command_reply   设备 → 前端（QoS1；按 id 找回发起方）
  {"id":"c0ffee…","ok":true,"message":"开关已关闭"}
```

**上行链路：一条温度遥测的旅程。** 对照下图逐条读源码，你会第一次"看见"数据流：

```text
// 图示：遥测上行链路（括号内为源码位置）
[simulator.mjs]            [broker.mjs]              [浏览器 Vue 监控台]
 ① 每 4~8s 随机游走生成
   一条 JSON 遥测
  （reportSensor 函数）
      │
      │ ② QoS 0 发布到
      │    iot/gh01/gh01-001/up/telemetry
      ▼  ────── TCP 1883 ─────▶
                             aedes 按 Topic 匹配订阅者
                                 │
                                 │ ③ 同一个 broker 还挂着
                                 │    WebSocket 入口（8083 /mqtt）
                                 ▼  ───── WebSocket ─────▶
                                                      ④ mqtt.js 触发 message 事件
                                                        （connection.ts）
                                                            │
                                                      ⑤ IotGateway.route：
                                                        parseTopic 解析 + decodeTelemetry
                                                        校验/去重/纠时（codec.ts）
                                                            │
                                                      ⑥ devices store.ingestTelemetry：
                                                        追加进滑动窗口（上限 120 点，
                                                        stores/devices.ts）
                                                            │
                                                      ⑦ ECharts 追加一个点
                                                        （TelemetryChart.vue）
```

**下行链路：一次"关插座"的旅程。** 前端把它包装成了 RPC over MQTT 的模式：

```text
// 图示：控制下行链路（RPC over MQTT）
[ControlPanel.vue]      [services/mqtt/index.ts]     [broker.mjs]      [simulator.mjs]
 ① 用户点"开关"按钮
 ② publishCommand('switch')
    生成请求 id（uuid）
 ③ 按钮进入 pending
      │
      │ ④ QoS 1 发布
      ▼
    iot/pl01/pl01-001/down/command
      ─────────────────────────▶ aedes 转发 ─────▶ ⑤ handleCommand 执行
                                                    （setTimeout 300ms 模拟耗时）
                                                        │
      ⑩ Promise resolve：          ⑨ IotGateway.settle ◀┘ ⑥ 设备 QoS 1 发布
        ok / rejected / timeout      按 id 找回 pending ◀── iot/pl01/pl01-001/
        按钮状态更新，写指令日志       Promise                down/command_reply
```

三个结果状态值得记住：`ok`（设备确认执行）、`rejected`（设备拒绝，如阈值越界）、`timeout`（`commandTimeoutMs = 8000`ms 内没等到回执）。**MQTT 发布成功不等于设备执行成功**——中间任何一环都可能断，所以控制类交互必须等业务回执，而不是发完就亮绿灯。

## 1.1.4 部署形态与规模分级

落地时你大概率不会从零写平台层。两条路线的对比：

| 维度 | 公有云 IoT 平台（阿里云 IoT / 腾讯云 IoT / 华为云 IoT / AWS IoT Core） | 自建 Broker（EMQX / Mosquitto / aedes） |
| --- | --- | --- |
| 接入规模 | 百万级设备，免运维扩容 | 单机数百到数万，EMQX 集群可到百万级 |
| 协议与模型 | MQTT/CoAP/HTTP + 平台私有物模型 | 标准 MQTT，物模型自己定 |
| 前端对接 | 多为平台 REST API + 官方 WebSocket 通道 | 自由选择：直连 Broker over WebSocket 或自建 API |
| 设备安全 | 一机一密、动态注册、证书体系 | 自己设计认证与权限 |
| 运维成本 | 平托管，按消息量/设备数计费 | 自己负责集群、持久化、监控告警 |
| 数据主权 | 数据在云厂商 | 数据完全自持 |
| 适合场景 | 快速上线、设备量大、需要整套设备管理 | 数据合规敏感、深度定制、成本敏感、教学 |

demo 选 aedes 纯粹出于教学考虑：纯内存实现，`pnpm install` 一次到位，重启即清空，没有任何运维心智负担。真实项目的自建路线一般从 EMQX（企业级、带仪表盘）或 Mosquitto（轻量、久经考验）起步。无论哪条路线，**前端面对的 MQTT 语义是一样的**——本教程的技能可以直接迁移。

同一套架构，规模差几个数量级，前端的写法就完全不同：

| 规模 | 设备数 | 消息量级 | 典型拓扑 | 前端设计要点 |
| --- | --- | --- | --- | --- |
| 家庭级 | 10~100 台 | < 10 条/秒 | 单 Broker | 一条 WebSocket 直连即可；通配符全订阅 |
| 园区级 | 数百~数万 | 数百~数万条/秒 | Broker 集群 + 网关 | 快照 API + 增量订阅；前端去重/限流；图表降采样 |
| 城市级 | 十万以上 | 百万条/秒以上 | 多地域集群 + 流处理管道 | 前端不直连原始流：走平台 API 拉聚合结果/SSE；列表虚拟化 |

demo 是家庭级：8 台设备、每秒约 2~3 条报文，前端可以奢侈地"全量订阅 + 内存滑动窗口"。若把设备数乘上一万，`ingestTelemetry` 每秒要被调用上万次，不节流的 ECharts 会先死给你看。所以第 1.2 章讨论职责边界、第 4 章讨论性能时，都请带着这张表来思考。

## 运行与验证

跑通最小链路，并亲眼看到报文流：

```shell
# 文件: iot-tutorial-project/demo/（在项目根目录执行）
cd iot-tutorial-project/demo
pnpm install      # 首次运行先安装依赖
pnpm server       # 终端 1：同时拉起 Broker（1883/8083）与 8 台模拟设备
```

> 运行方式：终端 1 执行 `pnpm server`；另开终端 2 执行 `pnpm dev`；浏览器打开 http://localhost:5173（若被占用会顺延 5174，以终端输出为准）。

终端 1 应出现类似输出：

```text
# 期望输出（终端 1，来源: demo/server/index.mjs）
[broker] TCP 已就绪 mqtt://localhost:1883（设备侧）
[broker] WS  已就绪 ws://localhost:8083/mqtt（前端侧）
[simulator] 8 台设备正在接入 mqtt://localhost:1883
[device] gh01-001 上线（normal）
[broker] 接入 +  dev-gh01-001
[broker] dev-gh01-001 → iot/gh01/gh01-001/up/status (112B, qos1)
[broker] dev-gh01-001 → iot/gh01/gh01-001/up/telemetry (103B, qos0)
```

每一行报文日志的格式是：`客户端 id → Topic（载荷字节数, QoS 等级）`。对照 1.1.3 的上行链路图：`dev-gh01-001 → iot/gh01/gh01-001/up/telemetry` 就是链路的第 ② 步；浏览器页面上随后出现的曲线，是第 ④~⑦ 步的结果。观察两分钟，你还能看到：

- `gh01-003` 偶发一条 `up/event`（温度尖峰告警）；
- `gh01-002` 每 15 秒一次性上报 4 个缓存样本（低功耗批量剧本）；
- `gh01-006` 在启动约 40 秒后优雅下线（状态 + 事件双通道）；
- `gh01-004` 从始至终离线——它 retain 的就是 offline 状态。

## 最佳实践与常见坑

- **现象**：页面打开后设备列表一直是空的。
  **原因**：`VITE_MQTT_URL` 与 Broker 的 WS 入口对不上（比如只改了端口没改 [demo/.env.development](../../demo/.env.development)），或 Broker 根本没起来。
  **解法**：确认终端 1 有 `WS 已就绪 ws://localhost:8083/mqtt` 这行日志；修改 `.env.development` 后必须重启 `pnpm dev`（Vite 不会热更环境变量）。

- **现象**：Broker 重启后，页面上的设备状态停在旧值，新上报也不生效。
  **原因**：aedes 是内存实现，重启即清空所有保留消息；而浏览器里旧的组件状态、旧订阅还挂着。
  **解法**：刷新页面重新订阅。生产环境要靠"持久化 Broker + 快照查询 API"双保险，不能指望 retain 包打天下。

- **现象**：`pnpm server` 报端口占用（EADDRINUSE），起不来。
  **原因**：上一次的进程没退干净，或 1883/8083 被其他程序占用。
  **解法**：`lsof -i :8083` 找到占用进程 PID 后 `kill` 掉；或者改端口，并同步修改 `.env.development`。

- **现象**：遥测停了几秒就把设备标成离线并触发告警，过一会儿设备又"复活"。
  **原因**：把"错过一次上报"当成了"设备离线"。无线网络下丢一包是常态。
  **解法**：三重在线判定——设备自报 status、Broker 遗嘱、前端看门狗（demo 中 `offlineAfterMs = 45000`，每 5 秒巡检一次 `lastSeenAt`，见 [stores/devices.ts](../../demo/src/stores/devices.ts)）。三重判定都指向离线才告警，且同一次离线只报一次。

## 实操任务

1. **画一张你自己业务域的链路图**。选一个你熟悉的场景（共享单车、电梯监控、智能仓库都行），仿照 1.1.3 的两张 ASCII 图画出：设备是什么、Broker 在哪、前端用什么协议接入、上行有什么数据、下行有什么指令。提示：先把 Topic 契约定出来，链路图自然就清晰了。
2. **数报文、估日增量**。把 server 日志重定向到文件：`pnpm server 2>&1 | tee /tmp/broker.log`，运行整 10 秒后 Ctrl+C，用 `grep -c '→ iot/' /tmp/broker.log` 统计报文数。提示：结合上报周期估算日增量——普通传感器 4~8 秒一条、低功耗设备 15 秒批量 4 个样本、插座 3~6 秒一条，别忘了还有约 6% 的重复报文。
