## 4.3.1 网络故障谱系：四类故障，四种表现

"断网"不是一种故障，是一个谱系。先分类，才能对症：

| 故障 | 传输层表现 | 前端感知时机 | demo 对策 |
| --- | --- | --- | --- |
| 网线拔掉 / WS 被断 | close 事件立即或数秒内到达 | 秒级 | close → 退避重连 |
| Broker 重启 | 已有连接批量 close，重启后重连请求瞬间涌入 | 秒级 | 全抖动退避打散（4.3.2） |
| 移动网络切换（Wi-Fi↔蜂窝） | 旧连接"僵死"：TCP 未断但已不通，close 可能迟迟不来 | 分钟级 | 入站看门狗强制重连（4.3.3） |
| 页面后台被浏览器节流 | 定时器降频，keepalive 心跳可能被延迟 | 恢复前台后 | 长窗口看门狗 + 可见性讨论（4.3.4） |

这张表的关键洞察是：**close 事件不一定来**。前两类故障浏览器能及时告诉你；后两类里连接只是"名存实亡"——TCP 层面还活着，数据已经不通。只依赖 close 事件做重连的系统，在移动网络与后台标签页场景下会永远停在"已连接"的假象里。demo 为此准备了两套机制：close 驱动的退避重连，加上不依赖 close 的入站看门狗。

## 4.3.2 为什么弃用 mqtt.js 内置重连

demo 在连接参数里明确关闭了内置重连：

```ts
// 出处：demo/src/services/mqtt/connection.ts（connect 节选）
this.client = mqtt.connect(CONFIG.mqttUrl, {
  clientId,
  clean: true,
  keepalive: 30,
  reconnectPeriod: 0, // 关闭内置重连，由本类接管
  connectTimeout: 8_000,
})
```

mqtt.js 的内置重连是**等间隔重试**，且重连语义黑盒：失败原因不区分、重试节奏不可控、成功后无法注入自定义对账逻辑。对一个要面对"broker 重启后海量客户端同时重连"的监控台来说，等间隔重试是致命的——推演一遍重连风暴：

1. Broker 崩溃重启，1000 个前端同时收到 close；
2. 若所有客户端都固定 1 秒后重试 → 1 秒后 Broker 收到 1000 个并发 CONNECT；
3. Broker 再次过载崩溃 → 所有客户端再次同时重试 → 雪崩循环。

这就是"惊群"（thundering herd）。解法是**全抖动指数退避（full jitter exponential backoff）**：

```ts
// 出处：demo/src/services/mqtt/connection.ts（scheduleReconnect 节选）
this.attempt++
const ceiling = Math.min(MAX_BACKOFF_MS, BASE_BACKOFF_MS * 2 ** this.attempt) // 30s 封顶
const delay = Math.random() * ceiling // 全抖动：在 [0, ceiling] 内均匀随机
this.setState('reconnecting', this.attempt, reason)
this.destroyClient()
this.reconnectTimer = setTimeout(() => this.connect(), delay)
```

公式展开：`delay = random(0, min(30s, 1s × 2^attempt))`。第 1 次失败在 0~2 秒内随机，第 2 次在 0~4 秒，第 10 次封顶在 0~30 秒。相比"等间隔 + 抖动"（在固定值附近扰动），**全抖动把重连时间点在整个窗口内均匀摊开**：Broker 重启瞬间收到的是平滑的接入速率，而不是整点脉冲。这一策略是主流云厂商架构实践中的推荐做法（demo 注释同款结论）。`MAX_BACKOFF_MS` 30 秒封顶则保证恢复速度：最坏情况下 30 秒内必有一次重试。

逐档拆开看退避的爬坡过程：

| attempt | ceiling = min(30s, 1s × 2^attempt) | delay 均匀落在 |
| --- | --- | --- |
| 1 | 2s | 0 ~ 2s |
| 2 | 4s | 0 ~ 4s |
| 3 | 8s | 0 ~ 8s |
| 4 | 16s | 0 ~ 16s |
| ≥5 | 30s（封顶生效） | 0 ~ 30s |

还有一个容易忽略的角色：`connectTimeout: 8_000`。网络故障谱系里有第三种形态——SYN 发出去了但对方不应答，CONNECT 请求悬而不决，既没有 connect 也没有 close。connectTimeout 让 mqtt.js 在 8 秒后主动报错关闭，把这种"悬着的连接"也送回 close → 退避重连的循环里。没有它，一次网络黑洞就能让重连机制永久停摆。

两个配套细节同样出自 [connection.ts](../../demo/src/services/mqtt/connection.ts)：

**attempt 在 connect 成功时归零**——下一次故障从短退避重新爬坡，不会背着上次的 30 秒上限：

```ts
// 出处：connection.ts（节选）
this.client.on('connect', () => {
  this.attempt = 0 // 成功即清零
  this.lastInboundAt = Date.now()
  this.setState('connected')
  // …（重订阅与看门狗，见 4.3.3 / 4.3.4）
})
```

**destroyClient 防双事件重复调度**——`error` 之后通常紧跟 `close`，若两处都调度重连，定时器会排两个。demo 的分工是：error 只记日志，重连统一在 close 里调度；销毁旧 client 时先摘掉全部监听器再强制关闭：

```ts
// 出处：connection.ts（节选）
private destroyClient(): void {
  if (!this.client) return
  this.client.removeAllListeners() // 先摘监听：防止 end() 触发的 close 再次调度重连
  this.client.end(true) // true = 立即强制关闭，不等在途报文
  this.client = null
}
```

`end()` 则负责反向清理——置 `ended` 标志、清 reconnectTimer、停看门狗，保证应用卸载后不再有任何定时器回调引用旧 client（定时器泄漏是坑 4）。

## 4.3.3 入站看门狗：抓"没有 close 的假死"

keepalive 与看门狗经常被混为一谈，其实它们守护的是**两个方向**：

| | keepalive | 入站看门狗 |
| --- | --- | --- |
| 方向 | client → broker 发 PINGREQ 心跳 | broker → client 的业务报文 |
| 回答的问题 | "这条 TCP 连接还活着吗" | "这条连接还能给我送数据吗" |
| 抓不住的场景 | — | broker 进程假死但 TCP 未断、代理层静默吞连接、订阅被清空 |

keepalive 30 秒由 mqtt.js 自动维护，TCP 半开时它能感知一部分；但如果 Broker 进程 hang 住却不关 socket，心跳 PINGREQ 可能还有回应（或超时行为不确定），而**业务数据已经断流**——监控台上表现为"已连接，但曲线永远不动"。这正是看门狗的靶子：

```ts
// 出处：demo/src/services/mqtt/connection.ts（节选）
/** 入站看门狗：已连接但长时间收不到任何报文 → 判定假死并强制重连 */
private startWatchdog(): void {
  this.stopWatchdog()
  this.watchdogTimer = setInterval(() => {
    if (this._state !== 'connected') return
    if (Date.now() - this.lastInboundAt < INBOUND_WATCHDOG_MS) return
    this.stopWatchdog()
    this.scheduleReconnect('入站看门狗超时（连接假死）')
  }, WATCHDOG_TICK_MS) // 每 5s 检查一次
}
```

`lastInboundAt` 在 `connect` 成功与每条 `message` 到达时刷新——注意它数的是**任何入站报文**（包括别的设备的数据），不是某台设备的上报。**90 秒阈值（INBOUND_WATCHDOG_MS）的依据**：demo 设备 4~8 秒上报一次，90 秒静默意味着连续丢 10+ 条，正常网络不可能；同时 90 秒是 keepalive（30s）的三个周期，慢网络下不会误杀。触发后走的仍是 `scheduleReconnect`，UI 上能看到 reason："入站看门狗超时（连接假死）"。

与 keepalive 互补后，重连的触发源有两个：close 事件（传输层断开）与看门狗（数据层断流），两者都收敛到同一个退避调度入口。

## 4.3.4 重连成功后的三件恢复事务

连接恢复 ≠ 系统恢复。demo 在 `connect` 回调里依次完成三件事。

**第一件：显式重订阅。** demo 用 `clean: true`——会话不依赖 Broker 状态，行为可预期；代价是 clean 会话不保留订阅列表，**每次（重）连接成功后必须重新 subscribe**：

```ts
// 出处：connection.ts（节选）
// clean 会话不保留订阅 → 每次（重）连接成功后必须显式重订阅
this.client?.subscribe([...SUBSCRIBE_TOPICS], { qos: 1 }, (err) => {
  if (err) console.error('[mqtt] 订阅失败', err)
})
```

订阅清单来自 [topics.ts](../../demo/src/services/mqtt/topics.ts) 的 `SUBSCRIBE_TOPICS`（`iot/+/+/up/#` 与指令回执）。漏掉这一步的故障形态极具迷惑性：指示器显示"已连接"，但曲线停摆、告警不响——排查看门狗、排查 Broker 都找不到问题，其实只是订阅丢了（坑 2）。

**第二件：状态对账。** 断线期间错过的消息怎么办？demo 的答案是 **retained 保留消息**：设备上线时把档案以 retain 标志发布到 `up/status`（见 [simulator.mjs](../../demo/server/simulator.mjs)），Broker 为每个主题保留最后一条。前端重连 + 重订阅的瞬间，Broker 立即补发全部 retained status——设备清单、名称、在线状态自动恢复，前端不需要任何额外请求。retained 在这里的妙用：**把"订阅"变成了"快照查询"**。低功耗设备 15 秒才一条遥测，retained status 让前端首屏秒出完整设备列表。

retained 只能补"最后一条"，历史遥测补不了。生产环境的强化方案是重连后拉一次 REST 快照做权威对账：

```ts
// 生产扩展示例（demo 未实现）：重连成功后拉一次快照对账
this.client.on('connect', async () => {
  this.client?.subscribe([...SUBSCRIBE_TOPICS], { qos: 1 })
  const snap = await fetch('/api/devices/snapshot').then((r) => r.json())
  devices.reconcile(snap) // 用服务端权威数据覆盖本地滑窗/在线状态
})
```

对账原则是**快照覆盖本地，而不是合并**：断线期间的本地推导（如看门狗判定的离线）可能已经过时，权威数据在服务端。

**第三件：UI 状态机呈现。** 连接层的状态经 [connection.ts（store）](../../demo/src/stores/connection.ts) 暴露给 UI：`idle → connecting → connected ⇄ reconnecting → closed` 五态，附 attempt 与 detail。把 demo 的状态流转画成图：

```text
// 出处：demo/src/stores/connection.ts（状态注释）与 connection.ts 行为整理
// idle ──connect()──▶ connecting ──on('connect')──▶ connected
//                        │                            │
//                        │ on('close') / 看门狗超时     │ on('close') / 看门狗超时
//                        ▼                            ▼
//                     reconnecting ──on('connect')──▶ connected（attempt 归零）
//
// 任意状态 ──end()──▶ closed（ended 标志置位，不再重连）
```

[ConnectionIndicator.vue](../../demo/src/components/ConnectionIndicator.vue) 把它翻译成人话：

```vue
<!-- 出处：demo/src/components/ConnectionIndicator.vue（节选） -->
case 'reconnecting':
  return `重连中（第 ${conn.attempt} 次）`
```

"第 N 次"的递增给用户"系统在自愈"的信号，也给 4.4 章的监控埋点（重连次数上报）提供数据源。

**visibilitychange 的取舍讨论。** 浏览器对后台标签页有节流：定时器最低频次受限，看门狗的 5 秒 tick 可能被拉长；页面 freeze 期间网络栈也可能停摆，回到前台的瞬间 `lastInboundAt` 已经过期——看门狗可能误判"假死"触发一次多余重连。两种策略：

- 保守：后台暂停看门狗判定，恢复可见时重置基线（生产扩展示例）；
- 激进：不处理——误判的代价只是一次退避重连，可接受。

demo 选择不处理（90 秒窗口足够长，常规后台节流不会误杀），这是讨论过的取舍而非遗漏。若要处理，思路如下：

```ts
// 生产扩展示例（demo 未实现）：可见性恢复时重置看门狗基线
// MqttConnection 需暴露 resetWatchdogBaseline()：内部 lastInboundAt = Date.now()
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible') {
    conn.resetWatchdogBaseline()
  }
})
```

## 运行与验证

完整演练一遍断网恢复，全程观察四个证据点：

1. 启动环境：终端 A `pnpm server`（Broker + 8 台设备），终端 B `pnpm dev`，浏览器确认"已连接"、曲线滚动；
2. **杀 Broker**：在终端 A 按 Ctrl+C。观察指示器数秒内变"重连中（第 1 次）"，次数持续递增；重连间隔肉眼可见地变长**且两次演练的节奏不同**（全抖动的随机性）；
3. **重启 Broker**：再次 `pnpm server`。15~30 秒内指示器应回到"已连接"，**不刷新页面**的情况下：设备名称/在线状态自动恢复（retained status 对账生效）、曲线出现新数据点（重订阅生效）；
4. **对证据 Broker 日志**：出现一行 `[broker] 接入 + web-console_xxxxxxxx`——随机后缀的 web-console 重新接入，这就是重连成功的铁证。

```text

// [broker] TCP 已就绪 mqtt://localhost:1883（设备侧）

// [broker] web-console_7xk2p9 → iot/gh01/gh01-001/up/telemetry (…B, qos0)  ← 数据链路恢复
```

## 最佳实践与常见坑

**坑 1：重连风暴（无抖动退避）**
现象：Broker 每次重启后"二次崩溃"，或重启后大量客户端连接失败。
原因：客户端用固定间隔重试，Broker 重启瞬间收到集中冲击；过载再次崩溃后客户端再次同时重试，形成雪崩循环。
解法：全抖动指数退避（0 ~ min(30s, 1s×2^attempt) 均匀随机）+ 退避封顶；服务端侧再配连接速率限制双保险。

**坑 2：重连后忘记 resubscribe**
现象：指示器显示"已连接"，但图表停摆、告警不响，重启前端才恢复。
原因：clean 会话重连后订阅列表为空，Broker 不会替你恢复；"连上"只代表链路通，不代表数据通。
解法：把 subscribe 放进 connect 成功回调（demo 写法），任何一次（重）连接都走同一条路径；这也是"重连后三件事"必须串成固定流程的原因。

**坑 3：close/error 双事件重复调度**
现象：attempt 一次断线跳升 2，重连定时器排了两个，日志出现成对的重连记录。
原因：mqtt.js 里 `error` 之后通常紧跟 `close`，两处都调用 scheduleReconnect 就会双调度。
解法：职责分离——error 只记日志，重连统一挂在 close（demo 的分工）；销毁旧 client 前 `removeAllListeners()`，切断 end() 引发的二次 close。

**坑 4：定时器泄漏**
现象：应用卸载/页面离开后，控制台仍打出重连日志；内存随反复进出页面持续增长。
原因：reconnectTimer / watchdogTimer 未清理，回调闭包引用着旧 client 实例，对象无法回收。
解法：`end()` 统一清理（ended 标志 + clearTimeout + stopWatchdog + destroyClient），并在应用卸载钩子里调用；看门狗每次 startWatchdog 前先 stopWatchdog，杜绝叠加。
