## 4.2.1 量级估算：先把"海量"变成数字

"海量设备"不是形容词，是一道乘法题：

```text
消息速率 = 设备数 × 上报频率（每设备每秒消息数）
```

demo 的 8 台设备（4~8 秒随机上报）约 1.3 条/秒——这是教学基线。把规模放大三档看压力：

| 设备数 | 上报间隔 | 消息/秒 | 每分钟消息 | 前端必须具备 |
| --- | --- | --- | --- | --- |
| 8（demo） | 4~8s | ≈1.3 | ≈80 | 无压力，正确性优先 |
| 500 | 5s | 100 | 6 000 | 批量渲染必须有 |
| 5 000 | 5s | 1 000 | 60 000 | Worker 解析 + 虚拟列表 + 降采样 |

前端的预算从帧来：60fps 意味着每帧只有 **16.6ms**，其中还要扣掉样式计算、布局、绘制。留给"处理一条消息"的时间摊下来不足 0.5ms——而一次完整的 ECharts setOption 重绘轻松超过 5ms。结论很直白：**100 条/秒的消息流里，逐消息触发渲染必然卡死**。demo 的答案不是把每条消息处理得更快，而是让消息根本不直接触发渲染——分四层把消息流"降频"。

## 4.2.2 demo 已实现的四层分流

先给总览，再逐层对照源码讲：

| 层 | 策略 | 代码位置 | 解决的问题 |
| --- | --- | --- | --- |
| 内存层 | 滑窗上限 120，批量裁剪 | [devices.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/stores/devices.ts) | 长会话内存无限增长 |
| 渲染层 | 800ms 批量 setOption | [TelemetryChart.vue](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/components/TelemetryChart.vue) | 消息频率与渲染帧率耦合 |
| 状态层 | lastSeen 用接收时刻 + 5s 看门狗 | [devices.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/stores/devices.ts) | 逐消息状态翻转 |
| 告警层 | 60s 冷却去重 + 容量 200 | [alerts.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/stores/alerts.ts) | 告警风暴 |

**内存层：滑窗上限。** 每台设备的遥测只保留最近 120 个点（`CONFIG.windowCap`），超出部分一次性裁剪：

```ts
// 出处：demo/src/stores/devices.ts（ingestTelemetry 节选）
// 滑窗裁剪：一次性删除超出上限的最旧数据（splice 比循环 shift 高效）
if (e.window.length > CONFIG.windowCap) {
  e.window.splice(0, e.window.length - CONFIG.windowCap)
}
```

两个细节：一是**上限让每设备内存恒为 O(1)**——跑一整天和跑一分钟占用相同；二是**批量裁剪**而非逐条 shift——每来一条消息 shift 一次是 O(n) 数组搬移，还多触发一次响应式更新；攒到超限后一次 splice 删掉超额段，写放大最小。监控台的价值在"看当前趋势"，120 点足够；历史回看属于查询类需求，走接口而不是把全量数据养在内存里。

**渲染层：800ms 批量。** 消息到达只写 store，图表按固定节奏从滑窗取数：

```ts
// 出处：demo/src/components/TelemetryChart.vue（节选）
let timer: ReturnType<typeof setInterval> | null = null
onMounted(() => {
  render()
  timer = setInterval(render, 800)
})
```

`render()` 每次从 `entry.window` 读全量滑窗重新 setOption。这一层把"每秒 N 条消息"与"图表帧率"彻底解耦：消息再快，渲染频率恒定约 1.25 帧/秒。组件注释里还有一句 `notMerge` 保证设备切换后序列不残留——那是正确性问题，本层解决的是性能问题，两者都靠"从 store 快照重建"这一招实现。

**状态层：接收时刻 + 看门狗。** 遥测到达时只做两件便宜的事——更新 `lastSeenAt` 数值和 `latest` 引用，**不**直接翻转在线状态：

```ts
// 出处：demo/src/stores/devices.ts（节选）
// lastSeen 用本地接收时刻：设备时钟可能漂移，不能信它的时间戳
e.lastSeenAt = Date.now()
```

在线状态的切换交给 5 秒一 tick 的看门狗批量判定（超过 `CONFIG.offlineAfterMs` 45 秒无上报才置离线）。收益有两层：性能上，状态写入从"每条消息一次"降为"每 5 秒一轮扫描"，订阅 online 的 UI 不会被高频重渲染；正确性上，接收时刻天然免疫设备时钟漂移（漂移的处理在 codec 层，见 4.4 章）。

**告警层：冷却去重。** 同设备同告警码在 60 秒冷却窗口内只收第一条，且总量上限 200 条：

```ts
// 出处：demo/src/stores/alerts.ts（push 节选）
const key = `${input.deviceId}:${input.code}`
const last = lastByKey.get(key)
if (last !== undefined && now - last < DEDUPE_WINDOW_MS) return
```

没有这层的后果可以推演：一台温度传感器的尖峰剧本以 4~8 秒周期触发 `TEMP_HIGH`，一小时能产生 500+ 条告警——列表 DOM 崩、真实告警被淹没、用户开始忽略告警（"狼来了"效应）。冷却窗口 + 容量上限让告警中心**有界**。

## 4.2.3 进阶手段（生产扩展，demo 未实现）

以下是设备规模上去之后的候选清单。**每一条都要有实测数据支撑再上**，顺序按"性价比"排列。

**一、rAF 合帧 flush。** 800ms 定时的一个小缺陷是"没数据也渲染"。改成脏标记 + requestAnimationFrame：消息到达只置 dirty，浏览器下一帧统一 flush——天然对齐渲染节拍，后台标签页自动暂停：

```ts
// 生产扩展示例（demo 未实现）：rAF 合帧替代固定 800ms 轮询
let dirty = false
let rafId = 0

function scheduleFlush(): void {
  if (dirty) return
  dirty = true
  rafId = requestAnimationFrame(() => {
    dirty = false
    render()
  })
}

onUnmounted(() => cancelAnimationFrame(rafId))
```

取舍：800ms 定时实现最简单、渲染频率上限明确；rAF 更省但要注意两点——标签页回到前台时补一次 render（后台期间 rAF 被暂停），以及设备切换后强制 flush 一次。消息速率低时两者差距可忽略，先有数据再换。

**二、虚拟列表。** 设备卡片列表上到几千上万行时，DOM 节点数本身成为瓶颈。核心思想：只渲染可视区 ± 缓冲区的行，用总高度撑起滚动条：

```ts
// 生产扩展示例（demo 未实现）：虚拟列表核心思想示意
const ROW_H = 92
const visibleRows = computed(() => {
  const start = Math.max(0, Math.floor(scrollTop.value / ROW_H) - 5)
  const end = Math.min(list.value.length, start + Math.ceil(viewportH.value / ROW_H) + 10)
  return list.value.slice(start, end)
})
```

demo 的设备量（8 台）远用不到；社区方案成熟（如 VueUse 的 useVirtualList），不必手写。注意它与 4.2.2 的配合：虚拟列表解决"节点多"，滑窗解决"单节点数据大"，两个问题独立。

**三、Web Worker 中做 codec 解析。** JSON.parse 与字段清洗是纯 CPU 工作，量级上来后可移出主线程。mqtt.js 的 `payload` 是 Uint8Array，以 transferable 方式移交可避免结构化克隆的拷贝：

```ts
// 生产扩展示例（demo 未实现）：worker/codec.worker.ts —— 解析在 worker 线程完成
self.onmessage = (e: MessageEvent<{ topic: string; buf: ArrayBuffer; recvTs: number }>) => {
  const points = decodeTelemetry(new Uint8Array(e.data.buf), e.data.recvTs)
  self.postMessage({ topic: e.data.topic, points })
}
```

```ts
// 生产扩展示例（demo 未实现）：主线程 —— slice 出独立缓冲后以 transferable 移交
const buf = payload.buffer.slice(payload.byteOffset, payload.byteOffset + payload.byteLength)
worker.postMessage({ topic, buf, recvTs }, [buf]) // 第二个参数：转移所有权，零拷贝
```

两个工程细节：一是 codec.ts 里的 `codecStats` 是主线程的 reactive 对象，**不能直接进 worker**——worker 内改用普通计数，postMessage 回传后由主线程聚合；二是 TextDecoder/JSON.parse 在 worker 环境都可用，decode 逻辑几乎不用改。注意 transferable 移交后原 ArrayBuffer 不可再用，slice 这步复制是必要的（换来的是后续零拷贝）。

**四、ECharts 按需引入。** demo 的 [useECharts.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/composables/useECharts.ts) 用 `import * as echarts from 'echarts'` 全量引入——整个 ECharts 打进 chunk，构建日志里常见约 1MB 级别的 chunk 体积警告。demo 项目小、内网加载，可以接受；生产建议按需注册：

```ts
// 生产扩展示例（demo 未实现）：echarts/core 按需注册
import * as echarts from 'echarts/core'
import { LineChart } from 'echarts/charts'
import {
  GridComponent,
  LegendComponent,
  MarkLineComponent,
  TooltipComponent,
} from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'

echarts.use([LineChart, GridComponent, LegendComponent, MarkLineComponent, TooltipComponent, CanvasRenderer])
```

对照 TelemetryChart.vue 用到的能力选组件：折线（LineChart）、网格/图例/提示（三个 Component）、**阈值线 markLine 对应 MarkLineComponent**——漏了它阈值线会静默不渲染，这是按需引入最常踩的隐形坑。通常能把 ECharts 相关体积砍掉一大半。

**五、LTTB 降采样思想。** 滑窗扩到历史回看（几千点）时，绘制点数成为瓶颈。LTTB（Largest-Triangle-Three-Buckets）的思路是把 N 个点均分成若干桶，每桶选出"与前后相邻点构成三角形面积最大"的代表点——视觉形状基本不变，点数从 N 降到桶数：

```text
// 生产扩展示例（demo 未实现）：LTTB 核心思想示意（伪代码）
// 1) 将窗口按点数均分为 bucketCount 桶（首尾点必选）；
// 2) 对每桶计算「前一已选点 — 桶内候选点 — 下一桶平均点」的三角形面积；
// 3) 取面积最大者为该桶代表 —— 峰谷被保留，平坦区被压缩。
```

demo 滑窗上限 120 点，完全不需要；它在"图表要画几千点"的场景才值得引入。原则同全章一致：先量化，再优化。

**六、immutable 更新与深层 reactive 的取舍。** demo 的选择是"可变数组 + 批量读"：`window.push/splice` 直接改深层 reactive 数组，图表定时读快照。另一种风格是每次消息都做不可变替换（`window = [...window, p].slice(-120)`）——对 computed 缓存友好，但每条消息一次数组拷贝与响应式触发。高频写入流下，"可变写 + 批量读"通常更优。真正的红线是**不要 deep watch 滑窗**（见坑 2）：Vue3 的深层 reactive 数组一被 deep watch，每条 push 都触发 120 点的深度遍历比对，比不优化还慢。

## 最佳实践与常见坑

**坑 1：逐消息 setOption**
现象：设备一多，图表卡成幻灯片，主线程火焰图被 setOption 填满。
原因：每条消息触发一次 setOption，而 ECharts 内部的 diff + 重绘成本远高于单条消息本身的处理成本；100 条/秒的消息流等于每秒 100 次全量重绘。
解法：消息只写 store，渲染批量做——demo 用 800ms 定时，进阶用 rAF 合帧。判断标准：渲染频率与消息频率必须解耦。

**坑 2：用 deep watch 监听滑窗数组**
现象：CPU 占用随消息速率线性上涨，空闲时段也降不下来。
原因：`watch(() => entry.window, cb, { deep: true })` 在每次 push/splice 后都要深度遍历最多 120 个点做比对，高频消息下这是纯浪费。
解法：不 watch 数据本身。低频轮询快照（demo 的 800ms render）或以 `lastSeenAt` 这类标量为触发源的浅 watch；确实需要响应数据变化时，watch 派生标量（如 `window.length`）。

**坑 3：为"可能的大数据"过早 Worker 化**
现象：demo 阶段就引入 Worker，代码复杂度上升，实测反而更卡。
原因：8 台设备约 1.3 条/秒，postMessage 的序列化开销与统计聚合的复杂度超过收益；优化没有数据支撑。
解法：先跑 Performance 拿到长任务与耗时分布，确认解析确实占了主线程大头再上 Worker。把"Worker 化"留在设备规模 ≥ 千级的清单里（对照 4.2.1 的估算表），而不是现在。

## 实操任务

**任务 1：给 ConnectionIndicator 增加消息速率显示。** 用 codecStats 的 received 做增量采样，让性能压力从"感觉"变成"数字"（以下为实操参考，demo 未实现，其余样式与原文件一致）：

```vue
<!-- 实操参考（demo 未实现）：demo/src/components/ConnectionIndicator.vue 扩展版 -->
<script setup lang="ts">
import { computed, onUnmounted, ref } from 'vue'

import { codecStats } from '@/services/mqtt/codec'
import { useConnectionStore } from '@/stores/connection'

const conn = useConnectionStore()

const label = computed(() => {
  switch (conn.state) {
    case 'connected':
      return '已连接'
    case 'connecting':
      return '连接中…'
    case 'reconnecting':
      return `重连中（第 ${conn.attempt} 次）`
    case 'closed':
      return '已断开'
    default:
      return '未启动'
  }
})

const cls = computed(() => ({
  'is-connected': conn.state === 'connected',
  'is-busy': conn.state === 'connecting' || conn.state === 'reconnecting',
  'is-dead': conn.state === 'closed',
}))

// —— 实操扩展：每 2s 采样 received 增量 → 消息/秒 ——
const rate = ref(0)
let lastReceived = codecStats.received
const rateTimer = setInterval(() => {
  rate.value = Math.round((codecStats.received - lastReceived) / 2)
  lastReceived = codecStats.received
}, 2000)
onUnmounted(() => clearInterval(rateTimer))
</script>

<template>
  <div class="conn" :title="conn.detail || conn.state">
    <div class="conn-row">
      <span class="conn-dot" :class="cls" />
      <span class="conn-label">{{ label }}</span>
    </div>
    <div class="conn-sub">
      解析 {{ codecStats.decoded }} · 丢弃 {{ codecStats.dropped }} · {{ rate }} msg/s
    </div>
  </div>
</template>

<!-- style 部分与原文件一致，此处省略 -->
```
