## 4.1.1 威胁模型：监控台"裸奔"时会遇到什么

先把 demo 的连接现状摆上台面：

```text
// 出处：demo/server/broker.mjs（节选）
//   - TCP 1883       ：设备侧原生 MQTT 入口（模拟器等）
//   - WS  8083 /mqtt ：浏览器侧 MQTT over WebSocket 入口
// 两个入口都没有 TLS，也没有任何用户名/密码校验 ——
// 任何客户端都能连上来，订阅任何主题，发布任何主题。
```

> 运行方式：cd demo && pnpm server，观察启动日志中两个入口的声明

基于这套现状直接部署到真实网络，至少要面对四类威胁：

| 威胁 | 攻击路径 | demo 现状 | 生产对策 |
| --- | --- | --- | --- |
| 窃听 | 同网段抓包，直接读到遥测明文与控制指令 | ws:// 明文传输 | wss + TLS（4.1.2） |
| 伪造 clientId 抢占 | 用相同 clientId 连入，把真连接挤下线后冒名收发 | 前端有随机后缀，设备侧可预测 | 认证 + 随机化（4.1.3） |
| 越权发布订阅 | 任意客户端订阅 iot/# 读全网数据，或发布 down/command 控制设备 | Broker 无 ACL | Topic 级 ACL（4.1.3） |
| 重放 | 抓到一条开泵指令，原样重发 | 无时间戳/序号校验 | 短期凭证 + 应用层防重放（4.1.3） |

**威胁一：窃听。** ws:// 是明文协议，同一 Wi-Fi 下任何设备抓包即可看到全部遥测、设备 IP 与控制指令。大棚温湿度泄露看似无害，但报文里若有水泵启停、卷帘开合指令，窃听就是控制劫持的第一步——攻击者不需要破解，只需要"看见并模仿"。

**威胁二：伪造 clientId 抢占。** MQTT 规定同一 clientId 的两个连接互踢。demo 前端已经做了防御的一半：

```ts
// 出处：demo/src/services/mqtt/connection.ts（节选）
// 每次连接追加随机后缀，避免多标签页/多窗口互相挤掉线
const clientId = `${CONFIG.clientIdPrefix}_${Math.random().toString(36).slice(2, 10)}`
```

但随机后缀只防"自己人互踢"，不防攻击者：模拟设备的 clientId 是完全可预测的 `dev-gh01-001`（见 [simulator.mjs](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/server/simulator.mjs)）。无认证时，任何人用同一个 id 连入即可把真设备挤下线，再以它的身份发布伪造数据——而前端看不出来。

**威胁三：越权发布订阅。** demo 的 aedes Broker 没有配置任何 ACL。前端只订阅了自己关心的主题（`iot/+/+/up/#` 等），但这是"礼仪"而不是"权限"——一个恶意客户端同样能 `subscribe('iot/#')`，甚至向 `iot/+/+/down/command` 发布重启指令。

**威胁四：重放。** 即使加了认证，抓到一条 `{ id, action: 'switch', params: { on: true } }` 后原样重发，Broker 与设备都无法分辨这是新指令还是旧报文。MQTT 协议本身不提供防重放语义，必须靠应用层解决（短期凭证 + 指令时间戳/序号，见 4.1.3 末尾）。

## 4.1.2 传输加密：从 ws:// 到 wss://

**先声明教学边界：demo 的 ws:// 仅限本机开发。** localhost 上的"窃听者"只有你自己，教学取舍可以接受；一旦地址离开 127.0.0.1（哪怕是内网 192.168.x.x），必须换成 wss。

wss 没有任何新协议，就是"TLS 包裹的 WebSocket"：握手与数据全部走加密通道。加密的信任基础是**证书链**——浏览器信任库里的根证书 → 中间证书 → 你的域名证书，逐级签名。链条上任何一环对不上，握手即失败。

| 方案 | 成本 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 自签证书 | 零成本，自己生成 | 内网 POC、封闭设备网络 | 每个客户端都要手动信任根证书，流程易出错 |
| 公网 CA（含免费签发渠道） | 域名 + 定期续期 | 一切有域名的生产部署 | 续期过期会导致全量掉线，需监控证书有效期 |

**浏览器对 wss 自签证书的处理是最阴的坑**：HTTPS 页面遇到自签证书会弹警告页让你点"继续访问"，而 wss 握手**不弹任何确认框**——证书校验失败直接 close，前端只会看到无限"重连中（第 N 次）"，控制台连具体原因都很少给。解法只有两条：先用 https 访问同一域名（含端口）手动信任一次证书，浏览器会记住；或者把自签根证书装入操作系统/企业设备的信任库。生产环境更推荐直接用公网 CA 签发，省掉整套信任流程。

生产部署的标准形态是**接入层终结 TLS**，后端 Broker 仍走内网明文：

```text
// 生产扩展示例（demo 未实现）：TLS 在接入层终结
// 浏览器 ──wss://iot.example.com/mqtt──▶ Nginx / API 网关（443，挂 TLS 证书）
//                                           └─ 反向代理 → 内网 ws://broker:8083/mqtt
```

前端代码只需要换 URL，连接参数与 demo 完全一致：

```ts
// 生产扩展示例（demo 未实现）：连接 wss 入口（参数对照 connection.ts）
this.client = mqtt.connect('wss://iot.example.com/mqtt', {
  clientId,
  clean: true,
  keepalive: 30,
  reconnectPeriod: 0, // 重连仍由 MqttConnection 接管（见 4.3 章）
  connectTimeout: 8_000,
})
```

## 4.1.3 认证方案对比与授权 ACL

### 认证：四种方案怎么选

| 方案 | 做法 | 凭证泄露影响 | 接入成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| Broker 用户名密码 | 连接参数带 username/password | 长期有效，泄露即失控 | 最低 | 内网、原型验证 |
| 接入层签发短期 token | 用户登录换 token，Broker/网关校验 | 短期，过期自动失效 | 中 | 生产推荐基线 |
| 一次性 clientId 票据 | 每次连接先取一次性票据，票据即临时身份 | 仅一次连接有效 | 中高 | 高安全要求场景 |
| JWT 过期刷新 | JWT 作为凭证，过期前静默换新重连 | 短期，需处理刷新竞态 | 中高 | 有用户体系的平台 |

四种方案殊途同归，共同原则只有一条：**前端绝不存长效密钥**。浏览器端的一切存储都可被读取——DevTools 一眼可见、XSS 可窃取、恶意扩展可扫荡。长效密钥放在前端，等于把钥匙粘在门上。短期凭证的价值是把泄露窗口从"永久"压缩到"分钟级"：token 只放内存变量（刷新页面重新换取），localStorage 里最多放"如何换取 token"的非敏感配置。

### 授权：Topic 级 ACL 权限表

认证解决"你是谁"，ACL 解决"你能碰哪些主题"。按 demo 的 Topic 契约（`iot/{productId}/{deviceId}/{dir}/{kind}`，见 [topics.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/services/mqtt/topics.ts)）设计权限表：

| 主体 | 允许发布 | 允许订阅 | 其余主题 |
| --- | --- | --- | --- |
| 设备 {p}/{d} | `iot/{p}/{d}/up/#`、`iot/{p}/{d}/down/command_reply` | `iot/{p}/{d}/down/command` | 一律拒绝 |
| 前端监控台 | `iot/+/+/down/command`（可限定产品） | `iot/+/+/up/#`、`iot/+/+/down/command_reply` | 一律拒绝 |
| 未认证连接 | 连接直接拒绝 | — | — |

两点设计意图值得展开：

- **设备只能发布自己的 `up/#`**：一台被攻陷的设备无法伪造别的设备的数据，也无法向别的设备下发指令。记忆口径是"发布自己的 up、订阅自己的 down"，落地时建议精确到 kind——demo 契约里指令回执（`down/command_reply`）由设备发布，严格的 ACL 应把这一条也授给设备。
- **前端订阅面越窄，泄露面越小**：[topics.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/services/mqtt/topics.ts) 注释里写过"前端不订阅 down/command"——前端只关心回执，不回声自己发出的指令。ACL 把这条"礼仪"固化成"权限"。

落到具体 Broker 时，ACL 的配置形态大同小异：规则 = 主体（用户名/clientId 匹配模式）+ 动作（publish/subscribe）+ 主题通配符 + 允许/拒绝。以下为通用形态示意——**具体字段名与配置位置以你所用 Broker（如 EMQX 一类产品）的对应版本文档为准，此处不保证具体配置键**：

```text
// 生产扩展示例（demo 未实现）：Broker ACL 的通用配置形态示意
// 规则 1：设备身份（username 形如 dev_{productId}-{deviceId}）
//         publish   allow   iot/{productId}/{deviceId}/up/#
//         publish   allow   iot/{productId}/{deviceId}/down/command_reply
//         subscribe allow   iot/{productId}/{deviceId}/down/command
// 规则 2：前端身份（username = web-console，携带角色声明）
//         publish   allow   iot/+/+/down/command
//         subscribe allow   iot/+/+/up/#
//         subscribe allow   iot/+/+/down/command_reply
// 规则 3：兜底
//         其余一切动作/主题 → deny
```

### 防重放：最小应用层方案

demo 的指令报文已带 `issuedAt`（见 [index.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/services/mqtt/index.ts) 的 `publishCommand`），这是防重放的地基。补齐只需两步：设备侧拒绝 `issuedAt` 距今超过阈值（如 30 秒）的指令；配合 4.4 章的 mid 去重，抓包重发的旧指令会被时间窗与去重双重拦下。

## 4.1.4 前端侧安全清单

**一、敏感字段脱敏展示。** 设备档案里的 `ip` 字段（192.168.1.23）在共享大屏、投屏演示时应当脱敏：

```ts
// 生产扩展示例（demo 未实现）：IPv4 脱敏工具
export function maskIp(ip?: string): string {
  if (!ip) return '-'
  const parts = ip.split('.')
  if (parts.length !== 4) return ip
  return `${parts[0]}.${parts[1]}.${parts[2]}.*`
}
```

同理适用于经纬度、精确地址等一切"展示层不需要全量精度"的字段——脱敏放在展示函数里做，数据层保留全量，排查问题时不受影响。

**二、CSP 限制连接源。** 用 Content-Security-Policy 的 connect-src 把前端能发起的连接目标锁死，即使被注入恶意脚本也无法外传数据：

```html
<!-- 生产扩展示例（demo 未实现）：index.html 注入 CSP meta -->
<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'self'; connect-src 'self' wss://iot.example.com; img-src 'self' data:; style-src 'self' 'unsafe-inline'"
/>
```

注意：demo 本地用 ws://localhost:8083 联调时，若已上 CSP，必须把 `ws://localhost:8083` 也加进 connect-src，否则浏览器会直接拦截连接——这是"加了安全配置后本地突然连不上"的最常见原因。

**三、依赖供应链。** npm 包被投毒（仿冒包、 maintainer 账号失窃）是前端供应链的主要风险。基线动作：锁文件入库（demo 目录中已包含 pnpm-lock.yaml，生产要求它必须提交到版本库）；固定私有源；CI 安装一律 `pnpm install --frozen-lockfile`，保证"构建机器装到的依赖"与"你锁定的版本"完全一致；新增依赖前确认包名拼写与维护活跃度。

**四、localStorage 只放非敏感覆盖项。** 对照 [config.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/config.ts) 的设计：localStorage 只用于覆盖 Broker 地址这类**非敏感**配置，是教学联调的便利入口：

```ts
// 出处：demo/src/config.ts（节选）
//   localStorage.setItem('iot.mqttUrl', 'ws://192.168.1.100:8083/mqtt') 后刷新
function resolveMqttUrl(): string {
  const fromLS = typeof localStorage !== 'undefined' ? localStorage.getItem(LS_KEY) : null
  if (fromLS) return fromLS
  return import.meta.env.VITE_MQTT_URL || 'ws://localhost:8083/mqtt'
}
```

生产化的判断标准：某项数据泄露后"最坏能发生什么"。Broker 地址泄露——攻击者连不连得上是另一回事，低危；token/密钥泄露——直接失控，高危。前者可以放 localStorage，后者连放都不要放（内存变量 + 短期化）。

## 最佳实践与常见坑

**坑 1：token 放在 ws:// 查询串，被中间设备日志记录**
现象：安全审计发现 token 明文出现在反向代理/网关的 access log 里。
原因：`ws://host/mqtt?token=xxx` 这种写法把凭证放进了 URL，而 URL 会原样进入链路上每一跳的日志（代理、网关、抓包工具）；ws 明文阶段中间设备全都看得见。
解法：凭证放 MQTT CONNECT 报文的 username/password 字段（连接建立后才传输），或由接入层在代理转发时注入 header；**绝不放 URL 查询串**。对照"运行与验证"第 4 步检查 demo 的连接 URL。

**坑 2：clientId 可预测被抢占**
现象：某台设备频繁"掉线重连"，Broker 日志里同一 clientId 反复接入；或前端莫名被挤出会话。
原因：clientId 用了设备序列号等可预测值，另一实例（或攻击者）用同 id 连入触发 MQTT 互踢。
解法：双管齐下——clientId 加入随机成分（demo 前端在 connection.ts 已做），同时上认证（Broker 拒绝未授权连接后，"抢占"在源头失效）。

**坑 3：wss 自签证书静默失败**
现象：从 ws 切到 wss 后，前端无限"重连中（第 N 次）"，控制台只有 close 没有可读的错误详情。
原因：WebSocket 握手阶段的 TLS 校验失败，浏览器不弹窗、不重试提示，直接 close——表现与"服务端挂了"一模一样。
解法：先用 https 访问同一域名（含端口）手动信任证书，或改用公网 CA 签发的证书；排查时先在浏览器地址栏访问 wss 同源的 https 路径确认证书链是否可信。

**坑 4：CSP 上线后连不上 Broker**
现象：本地一切正常，上线后 WS 请求被浏览器直接拦截，Console 报 CSP 指令违规。
原因：connect-src 只配了 `'self'`，没包含 wss 的域名/端口；或本地联调的 ws:// 源忘记加入。
解法：connect-src 显式列出全部连接源（含端口）；上线前在 DevTools Console 观察是否有 CSP 违规报告，再逐条补齐。

## 实操任务

**任务 1：给 CONFIG 增加 wss 地址支持，并演示 localStorage 覆盖。**

在 [config.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/config.ts) 基础上扩展（以下为实操参考，demo 未实现，读者动手改）：

```ts
// 实操参考（demo 未实现）：demo/src/config.ts 的 wss 扩展
const LS_KEY = 'iot.mqttUrl'

// 假设接入层已在本机 8084 端口提供 wss（演示用预设）
const WSS_PRESET = 'wss://localhost:8084/mqtt'

function resolveMqttUrl(): string {
  const fromLS = typeof localStorage !== 'undefined' ? localStorage.getItem(LS_KEY) : null
  if (fromLS) return fromLS
  // 通过环境变量显式切换 wss 预设（真实环境由部署注入完整地址）
  if (import.meta.env.VITE_USE_WSS === '1') return WSS_PRESET
  return import.meta.env.VITE_MQTT_URL || 'ws://localhost:8083/mqtt'
}

export const CONFIG = {
  mqttUrl: resolveMqttUrl(),
  // clientIdPrefix / windowCap / defaultTempThreshold 等其余字段与原 config.ts 保持一致
} as const
```
