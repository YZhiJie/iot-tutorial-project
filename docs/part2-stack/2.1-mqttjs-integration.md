## 安装与 Vite 集成

### 安装依赖

demo 的依赖声明如下（节选）：

```json
// 文件: demo/package.json（节选）
{
  "dependencies": {
    "mqtt": "^5.16.1",
    "echarts": "^6.1.0",
    "pinia": "^4.1.0",
    "vue": "^3.5.44",
    "vue-router": "^5.4.0"
  }
}
```

> 运行方式：进入 `demo/` 目录执行 `pnpm install`，依赖声明已在 package.json 中，无需手动 add。

浏览器端接入 MQTT 有一个绕不开的前提：**浏览器没有原生 TCP socket**。MQTT 协议本身跑在 TCP 上，但网页里唯一可用的双向通道是 WebSocket，所以浏览器端的标准姿势是 **MQTT over WebSocket**。mqtt 5.x 会根据连接 URL 的协议自动选择传输层：`mqtt://` 走 TCP（仅 Node 环境可用），`ws://` / `wss://` 走 WebSocket（浏览器可用）。

demo 里两条链路分工明确（概念篇已讲，这里对照 demo 复述）：设备模拟器走 TCP `1883` 端口（真实设备也是 TCP/TLS 接入），浏览器走 WebSocket `8083` 端口，路径固定为 `/mqtt`。这个地址写在环境变量里：

```bash
# 文件: demo/.env.development
# 本地 Broker 的 WebSocket 入口（server/broker.mjs 提供）
VITE_MQTT_URL=ws://localhost:8083/mqtt
```

配置的消费端在 config.ts，采用「localStorage 覆盖 → 环境变量 → 兜底默认值」三级回退，方便联调时随时切换 broker 而不用改代码：

```ts
// 文件: demo/src/config.ts（节选）
function resolveMqttUrl(): string {
  const fromLS = typeof localStorage !== 'undefined' ? localStorage.getItem(LS_KEY) : null
  if (fromLS) return fromLS
  return import.meta.env.VITE_MQTT_URL || 'ws://localhost:8083/mqtt'
}
```

> 运行方式：联调远程 broker 时，在浏览器控制台执行 `localStorage.setItem('iot.mqttUrl', 'ws://192.168.1.100:8083/mqtt')` 后刷新页面即可生效。

### Vite 集成的关键一步：define global

新建 Vite 项目直接装 mqtt 5.x 后，浏览器控制台几乎必然报 `ReferenceError: global is not defined`。原因是 mqtt.js 的浏览器构建里引用了 Node 的全局对象 `global`，而 Vite 是纯浏览器 ESM 打包器，**不做任何 Node polyfill**，代码里没有任何人定义 `global`。demo 的解法是在 vite.config.ts 里做编译期替换：

```ts
// 文件: demo/vite.config.ts（节选）
/**
 * 坑点（docs 2.1）：mqtt.js 在浏览器构建里引用了全局 `global` 对象，
 * Vite 默认不做 Node polyfill，不注入会导致运行时 `global is not defined`。
 * 这里显式把它指到 `globalThis`。
 */
define: {
  global: 'globalThis',
},
```

`globalThis` 是 ES2020 标准的跨环境全局对象（浏览器和 Node 都有），把 `global` 字符串在打包时替换成它，mqtt.js 内部对 Node 全局的探测就能通过。注意：**修改 vite.config.ts 后必须重启 dev server**，define 是构建期行为，热更新不会生效。

## 连接参数逐个拆解

demo 把连接逻辑收敛在 `MqttConnection` 类里，核心连接代码如下：

```ts
// 文件: demo/src/services/mqtt/connection.ts（节选）
connect(): void {
  this.ended = false
  this.setState(this.attempt === 0 ? 'connecting' : 'reconnecting')
  const clientId = `${CONFIG.clientIdPrefix}_${Math.random().toString(36).slice(2, 10)}`
  // 关键参数解析见 docs 2.1；reconnectPeriod: 0 = 关闭内置重连，由本类接管
  this.client = mqtt.connect(CONFIG.mqttUrl, {
    clientId,
    clean: true,
    keepalive: 30,
    reconnectPeriod: 0,
    connectTimeout: 8_000,
  })
  // ……事件回调见下一节
}
```

五个参数逐个看：

| 参数 | demo 取值 | 含义与动机 |
| --- | --- | --- |
| clientId | `web-console_` + 8 位随机串 | MQTT 规定**同一 clientId 的两条连接会互踢**。每次连接追加随机后缀，多标签页 / 多窗口就不会互相挤掉线（见坑点 1） |
| clean | true | 不在 broker 侧保留会话与订阅列表。行为可预期、不依赖 broker 状态；代价是每次（重）连成功后必须**显式重新 subscribe**（下一节事件模型里能看到） |
| keepalive | 30（秒） | 每 30 秒一个 PINGREQ 心跳。broker 通常在约 1.5 倍周期内收不到心跳就判定客户端掉线 |
| reconnectPeriod | 0 | **关闭 mqtt.js 内置自动重连**，改由 `MqttConnection` 手动实现重连调度，动机见下文 |
| connectTimeout | 8000（毫秒） | 等待 CONNACK（连接确认报文）的超时。超时走 error / close，进入重连调度 |

关于 `reconnectPeriod: 0` 值得多说两句，这是 demo 最反直觉的一个配置。mqtt.js 默认内置指数退避重连，看起来"免费省事"，但 demo 选择关掉它、自己接管，注释里写明了三个理由：**全抖动指数退避**（`delay = random(0, min(30s, 1s × 2^attempt))`）能打散"服务端重启后海量客户端同时重连"的重连风暴；**入站看门狗**能识别"TCP 未断但数据不通"的连接假死；**clean 会话 + 每次重连后显式重订阅**让会话行为完全可预期。退避算法的实现细节与看门狗机制在第 4.3 章深挖，本章只需要记住：`reconnectPeriod: 0` 的含义是"重连这件事我自己负责"，异常断开后由 close 事件驱动 `scheduleReconnect()` 完成重连。

## 事件模型与订阅、发布

### 四类核心事件

mqtt.js 客户端是事件发射器，demo 用到了四个事件，恰好构成一条完整生命周期：

```ts
// 文件: demo/src/services/mqtt/connection.ts（节选）
this.client.on('connect', () => {
  this.attempt = 0
  this.lastInboundAt = Date.now()
  this.setState('connected')
  // clean 会话不保留订阅 → 每次（重）连接成功后必须显式重订阅
  this.client?.subscribe([...SUBSCRIBE_TOPICS], { qos: 1 }, (err) => {
    if (err) console.error('[mqtt] 订阅失败', err)
  })
  this.startWatchdog()
})

this.client.on('message', (topic, payload) => {
  this.lastInboundAt = Date.now()
  this.events.onMessage(topic, payload)
})

this.client.on('error', (err) => {
  // error 之后通常紧跟 close；这里仅记录日志，重连统一在 close 中调度（避免重复）
  console.warn('[mqtt] 连接错误：', err.message)
})

this.client.on('close', () => {
  this.stopWatchdog()
  if (this.ended) {
    this.setState('closed')
    return
  }
  this.scheduleReconnect('连接关闭')
})
```

- **connect**：CONNACK 握手成功。重连计数清零、状态切到 connected、立即重订阅（clean 会话的代价）、启动入站看门狗。
- **message**：收到订阅的主题报文。payload 是 `Uint8Array`（不自动解码 JSON），demo 刷新 `lastInboundAt` 后原样交给上层网关路由——解码是 codec 层的事，连接层不掺和。
- **error**：协议层/连接层错误。注意 demo 在这里**只记日志不做重连**——error 之后通常紧跟 close，重连统一在 close 里调度，否则会重复调度两个重连定时器。
- **close**：连接关闭（异常断开与服务端主动断开都会走到）。用 `ended` 标志区分"主动调用 end() 关闭"（页面卸载，不再重连）与"意外断开"（进入 `scheduleReconnect`）。

### 订阅与两级通配符

前端订阅清单只有两条，靠通配符覆盖全部 8 台设备的所有上行报文：

```ts
// 文件: demo/src/services/mqtt/topics.ts（节选）
/**
 * 前端订阅清单：两级通配符一次拿全部上行 + 指令回执
 * `#` 匹配剩余全部层级；`+` 匹配单层（MQTT 通配符语义见 docs 3.3）
 */
export const SUBSCRIBE_TOPICS = ['iot/+/+/up/#', 'iot/+/+/down/command_reply'] as const
```

主题契约是 `iot/{productId}/{deviceId}/{dir}/{kind}`，例如 `iot/gh01-002/up/telemetry`。对照通配符：

- `iot/+/+/up/#`：两个 `+` 分别匹配任意 productId、deviceId（各占**一层**），`#` 匹配 up 之后的**剩余全部层级**——telemetry、status、event 三种上行一网打尽。没有通配符的话，8 台设备 × 3 种上行 = 24 条订阅，新增产品还得改前端。
- `iot/+/+/down/command_reply`：指令回执单独订阅。注意前端**刻意不订阅 `down/command`**——那是自己发出去的指令，不回声。

### 发布 publish

发布端封装在连接层，未连接时直接抛错而不是静默丢包：

```ts
// 文件: demo/src/services/mqtt/connection.ts（节选）
publish(topic: string, payload: string, qos: 0 | 1 = 1): void {
  if (!this.client || !this.client.connected) {
    throw new Error('MQTT 未连接，无法发布')
  }
  this.client.publish(topic, payload, { qos })
}
```

调用方（网关）下发控制指令时用 QoS 1，并显式注释了取舍：

```ts
// 文件: demo/src/services/mqtt/index.ts（节选）
// QoS 1：指令必须送达（至少先到一次），遥测才用 QoS 0
this.conn.publish(commandTopic(productId, deviceId), JSON.stringify(msg), 1)
```

原则一句话：**必须到达的消息用 QoS 1（指令、状态、事件），高频可容忍丢失的遥测用 QoS 0**——为什么遥测敢用 0，第 2.4 章展开。

## 本地 Broker 联调

联调需要一个 broker。demo 自带了一个用 aedes 实现的内存版 broker（重启即清空），它同时开了设备侧和前端侧两个入口：

```js
// 文件: demo/server/broker.mjs（节选）
// 1) TCP 入口：设备侧原生 MQTT
createTcpServer(aedes.handle).listen(1883, () => {
  console.log('[broker] TCP 已就绪 mqtt://localhost:1883（设备侧）')
})

// 2) WebSocket 入口：浏览器侧 MQTT over WS
//    websocket-stream 把 WebSocket 包装成 aedes 需要的 duplex 流
websocketStream.createServer({ server: httpServer, path: '/mqtt' }, aedes.handle)
httpServer.listen(8083, () => {
  console.log('[broker] WS  已就绪 ws://localhost:8083/mqtt（前端侧）')
})
```

推荐用 `pnpm server` 一条命令同时拉起 broker 与 8 台模拟设备（内部先起 broker，延迟 800ms 让设备接入）：

```bash

pnpm server
```

> 运行方式：在 `demo/` 目录执行。它等价于同时运行 `pnpm broker` 与 `pnpm devices`，日志里能看到每一条 MQTT 报文。

## 最佳实践与常见坑

**坑 1：clientId 冲突互踢循环**
- 现象：开第二个标签页后，server 日志「接入 + / 断开 -」高频交替，两个页面的连接指示器轮流变「重连中」。
- 原因：MQTT 规定 broker 对相同 clientId 的新连接必须踢掉旧连接；两个客户端都开着自动重连，就形成「我连上 → 踢你 → 你重连 → 踢我」的死循环。
- 解法：clientId 永远带随机后缀（demo 的 `Math.random().toString(36).slice(2, 10)`）。排查互踢时看 server 日志里的 clientId 即可定位；同理，固定 clientId 的模拟器/调试客户端不要多开。

**坑 2：忘配 global，报 "global is not defined"**
- 现象：页面无连接，DevTools 控制台 `ReferenceError: global is not defined`。
- 原因：mqtt.js 的浏览器构建引用了 Node 全局对象 `global`，Vite 不做 Node polyfill，运行时无人定义它。
- 解法：vite.config.ts 中 `define: { global: 'globalThis' }`（demo 已配置），修改后**重启 dev server**。

**坑 3：broker WS 路径不匹配，反复 404**
- 现象：控制台反复出现 `WebSocket connection to 'ws://localhost:8083/' failed`，指示器永远「重连中」，重连计数一直涨。
- 原因：demo broker 的 WebSocket 入口挂在 `/mqtt` 路径（websocket-stream 的 path 参数），URL 漏写路径、或反向代理没转发该路径，握手都会被拒绝。
- 解法：URL 必须带全路径 `ws://localhost:8083/mqtt`；连远程 broker 用 `localStorage.setItem('iot.mqttUrl', 'ws://主机:8083/mqtt')` 覆盖后刷新，别改源码。

**坑 4：keepalive 撞上浏览器后台节流**
- 现象：标签页切后台几分钟，切回来发现指示器「重连中（第 N 次）」，server 日志里该 clientId 出现断开记录。
- 原因：浏览器对后台标签页的定时器做节流（可推迟到分钟级），PINGREQ 心跳被推迟超过 broker 容忍上限（约 1.5 倍 keepalive = 45 秒），broker 主动断开连接。
- 解法：这是浏览器机制不是 bug。演示时保持标签页前台；生产可适当调大 keepalive（如 60~120 秒）并接受"后台偶发重连"，不要写 hack 代码强行保活。
