## 在线状态的三重保障

监控面板最核心的问题是："这台设备到底在不在线？" demo 的答案是**不信任任何单一来源**，而是三重保障互相补位。

### 来源一：设备自报 status（QoS 1 + retain）

设备上线即发布档案，下线时发布离线状态。看模拟器的实现：

```js
// 文件: demo/server/simulator.mjs（节选）
client.on('connect', () => {
  // 上线即注册"设备档案"（保留消息）：前端订阅后立刻收到，无需等下一次上报
  publish(
    client,
    `${base}/up/status`,
    {
      online: true,
      name: def.name,
      product: { id: productId, name: PRODUCT_NAMES[productId] },
      fw: 'v1.4.2',
      ip,
    },
    { qos: 1, retain: true },
  )
})
```

`retain: true` 是关键：broker 会为每个主题保存最后一条保留消息，**前端刚订阅的瞬间就能拿到全部 8 台设备的最新状态**，不用干等下一轮上报。这就是为什么刷新页面后卡片立刻出现、gh01-004 立刻显示离线——它全程不发遥测，只有一条 retain 的 `{ online: false, reason: 'maintenance' }`。

### 来源二：遗嘱 LWT（broker 代发）

设备连接时向 broker 登记一条遗嘱：如果连接异常断开（断网、断电、进程崩溃，未发 DISCONNECT），由 broker 代发离线状态：

```js
// 文件: demo/server/simulator.mjs（节选：遗嘱）
const client = mqtt.connect(BROKER_URL, {
  clientId: `dev-${def.id}`,
  clean: true,
  keepalive: 30,
  reconnectPeriod: 3000,
  will: {
    topic: `${base}/up/status`,
    payload: JSON.stringify({ online: false, reason: 'connection_lost' }),
    qos: 1,
    retain: true,
  },
})
```

遗嘱同样带 retain，所以即使前端错过了"在线"报文，订阅时也能拿到最新的离线状态。

### 来源三：前端 lastSeen 看门狗（兜底）

前两类都依赖"有人通知你"。但真实世界存在**静默故障**：设备半死不活、TCP 连接还挂着、只有心跳没有数据，永远等不到离线报文。demo 在 store 里跑一个前端看门狗兜底：

```ts
// 文件: demo/src/stores/devices.ts（节选：前端离线看门狗）
function startWatchdog(): void {
  if (watchdogTimer) return
  watchdogTimer = setInterval(() => {
    const now = Date.now()
    for (const e of Object.values(map.value)) {
      if (e.online && e.lastSeenAt > 0 && now - e.lastSeenAt > CONFIG.offlineAfterMs) {
        setOnline(e, false, '上报超时，前端看门狗判定')
      }
    }
  }, 5000)
}
```

每 5 秒扫一轮，任何在线设备超过 `offlineAfterMs`（45 秒，config.ts）没发任何报文，就由前端推导为离线。

### 三级可信度

| 来源 | 触发方式 | 覆盖的故障 | 可信度 |
| --- | --- | --- | --- |
| 设备自报 status | 设备主动发布（QoS 1 + retain） | 计划内上下线、维护模式 | 最高：设备亲口说 |
| 遗嘱 LWT | broker 在连接异常断开时代发 | 断网、断电、进程崩溃 | 较高：broker 客观见证，但只覆盖「连接断了」 |
| 前端看门狗 | lastSeen 超 45 秒无任何上报 | 一切静默故障 + 前两类报文丢失 | 最低：前端推测，但是唯一兜底 |

store 还留了一道小兜底（devices.ts 的 ingestTelemetry）：即使设备从未发过 status，**只要遥测到达就视为在线**——status 报文丢了也不会误判。

## DeviceEntry：为消息流设计的数据结构

看 store 的数据结构决策，注释里写得非常清楚：

```ts
// 文件: demo/src/stores/devices.ts（节选）
export interface DeviceEntry {
  profile: DeviceProfile | null
  online: boolean
  /** 最近一次"收到消息"的本地时间（用接收时刻而非设备 ts，天然免疫时钟漂移） */
  lastSeenAt: number
  latest?: TelemetryPoint
  /** 遥测滑动窗口（时间升序），上限 windowCap */
  window: TelemetryPoint[]
  /** 温度告警阈值（setThreshold 指令可修改） */
  tempThreshold: number
  /** 智能插座开关状态 */
  on?: boolean
  /** 离线告警去重：同一次离线只报一次 */
  offlineAlerted: boolean
}
```

三个设计决策值得逐个理解：

1. **`Record<deviceId, DeviceEntry>` 做响应式根**：消息流是按 deviceId 高频写入的，普通对象键访问 O(1)，`devices.map['gh01-002']` 直接定位。列表展示用 `computed` 派生（`Object.values(map.value)`），不维护第二份数组，天然不会出现"列表和 map 不同步"。

   ```ts
   // 文件: demo/src/stores/devices.ts（节选）
   const list = computed(() => Object.values(map.value))
   const onlineCount = computed(() => list.value.filter((e) => e.online).length)
   const offlineCount = computed(() => list.value.length - onlineCount.value)
   ```

2. **滑窗上限 120**：遥测是无限流，不裁剪的话长会话内存无限增长。`windowCap`（config.ts 里 120）配合入库时的批量裁剪：

   ```ts
   // 文件: demo/src/stores/devices.ts（节选）
   // 滑窗裁剪：一次性删除超出上限的最旧数据（splice 比循环 shift 高效）
   if (e.window.length > CONFIG.windowCap) {
     e.window.splice(0, e.window.length - CONFIG.windowCap)
   }
   ```

3. **lastSeenAt 用本地接收时刻**：写入的是 `Date.now()`（收到报文那一刻），而不是报文里的设备时间戳。设备时钟可能漂移（低功耗设备偏移 90 秒，第 2.4 章会实测），"多久没听到它说话"只能以本机时钟为准。

## 状态机与告警联动

在线状态不是布尔值那么简单，online→offline 的**转换沿**才是业务关心的时刻——状态没变就反复告警会淹没告警中心。demo 用 `offlineAlerted` 标志做去重：

```ts
// 文件: demo/src/stores/devices.ts（节选）
function setOnline(e: DeviceEntry, online: boolean, reason?: string): void {
  const was = e.online
  e.online = online
  if (online) {
    e.offlineAlerted = false // 复位：下一次离线仍需告警
    e.lastSeenAt = Date.now()
    return
  }
  // online → offline 转换沿才推告警；offlineAlerted 保证同一次离线只报一次
  if (was && !e.offlineAlerted) {
    e.offlineAlerted = true
    useAlertsStore().push({
      deviceId: e.profile?.deviceId ?? '?',
      deviceName: e.profile?.name ?? e.profile?.deviceId ?? '?',
      level: 'warn',
      code: 'DEVICE_OFFLINE',
      message: `设备离线${reason ? `（${reason}）` : ''}`,
      fromDevice: false,
    })
  }
}
```

逻辑闭环：离线时若"之前是在线"（`was`）且"这次离线还没报过"（`!offlineAlerted`）才推告警；设备重新上线时 `offlineAlerted` 复位为 false，下一次离线照常报。所有来源（自报、遗嘱、看门狗）都汇入这同一个 `setOnline`，告警联动与去重只写一处。

## 视图层：统计条、过滤、卡片与指示器

### 统计条与搜索过滤：全部 computed 派生

DeviceListView 不持有任何设备数据副本，统计和过滤都是派生：

```vue
<!-- 文件: demo/src/views/DeviceListView.vue（节选） -->
<p class="page-sub">
  共 {{ devices.list.length }} 台 · 在线 {{ devices.onlineCount }} · 离线 {{ devices.offlineCount }} · 未读告警 {{ alerts.unreadCount }}
</p>
```

```ts
// 文件: demo/src/views/DeviceListView.vue（节选）
const keyword = ref('')
const filter = ref<'all' | 'online' | 'offline'>('all')

const filtered = computed(() =>
  devices.list.filter((e) => {
    const name = `${e.profile?.name ?? ''} ${e.profile?.deviceId ?? ''}`.toLowerCase()
    if (keyword.value && !name.includes(keyword.value.trim().toLowerCase())) return false
    if (filter.value === 'online' && !e.online) return false
    if (filter.value === 'offline' && e.online) return false
    return true
  }),
)
```

输入框 `v-model` 绑 keyword，computed 自动重算——没有手动监听 input 事件、没有手动维护"过滤后的列表"副本。

### "上报于 x 秒前"：页面级一个定时器

相对时间会过期，需要周期刷新。demo 的做法是**页面级一个定时器刷新 now，再作为 prop 下发给所有卡片**：

```ts
// 文件: demo/src/views/DeviceListView.vue（节选）
// 卡片"上报于 x 秒前"需要周期性刷新 now 触发重渲染
const now = ref(Date.now())
let timer: ReturnType<typeof setInterval> | null = null
onMounted(() => {
  timer = setInterval(() => (now.value = Date.now()), 5000)
})
onUnmounted(() => {
  if (timer) clearInterval(timer)
})
```

```ts
// 文件: demo/src/components/DeviceCard.vue（节选）
const props = defineProps<{ entry: DeviceEntry; now: number }>()
const seenText = computed(() =>
  props.entry.lastSeenAt > 0 ? `上报于 ${timeAgo(props.entry.lastSeenAt, props.now)}` : '尚未上报',
)
```

now 变化 → 依赖它的所有卡片 computed 重算 → 时间文案整体刷新。8 张卡片只有 1 个定时器（见坑点 2）。

## 最佳实践与常见坑

**坑 1：在线状态只信单一路源**
- 现象：设备死机但 TCP 连接未断，面板永远显示"在线"；或者 status 报文偶尔丢一次，明明在线却显示离线。
- 原因：只依赖设备自报（或只依赖 LWT）。自报覆盖不了静默故障，LWT 覆盖不了"连接还在但设备半死不活"。
- 解法：三重保障——自报 + 遗嘱 + lastSeen 看门狗（demo 阈值 45 秒，覆盖最长上报间隔的低功耗设备 15 秒一包还有余量），且全部汇入同一个 setOnline，告警去重只写一处。

**坑 2：列表页逐卡片 setInterval**
- 现象：设备一多页面明显变卡；DevTools 断点发现几十个定时器在跑；各卡片时间刷新节奏还不一致。
- 原因：把"时间流逝"的实现下放到每个卡片组件，N 张卡片 N 个定时器，N 倍重渲染。
- 解法：页面级一个 `now` 定时器 + prop 下发（DeviceListView 的写法），所有卡片的相对时间由同一个 now 驱动；定时器在 onUnmounted 清理。

**坑 3：Map 直接当响应式根**
- 现象：用 `ref(new Map())` 存设备表后，要么模板里没法直接 `Object.values` / JSON 序列化、调试不便；要么用了 `shallowRef`，改 `entry.online` 视图根本不更新。
- 原因：Map 需要专用方法遍历，工具链适配处处别扭；浅响应不追踪深层属性变更，而设备状态恰恰是深层高频变更。
- 解法：用普通对象 Record 做根 + 深层 ref（demo 的 `ref<Record<string, DeviceEntry>>({})`），键访问 O(1)、深层变更自动触发、`Object.values` 直接派生列表；键的建立统一走 `ensure()` 惰性创建，避免散落判空。

**坑 4：统计数字手动维护，和列表脱节**
- 现象：统计条显示"在线 7"，数一遍卡片只有 6 台在线；或过滤后统计数字不变。
- 原因：自己维护 `onlineCount` 变量，在某条路径漏更新；它与真值（map 里的数据）是两份状态。
- 解法：统计一律 computed 派生（`list.filter(e => e.online).length`），让 Vue 保证一致性，杜绝手写同步代码。
