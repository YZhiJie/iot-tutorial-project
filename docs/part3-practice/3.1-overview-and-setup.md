## 功能全景与章节地图

IoT Deck 是一个面向温室场景的设备监控台：8 台模拟设备（6 台温湿度传感器 + 2 台智能插座）持续上报数据，浏览器端实时展示、远程控制、汇聚告警。

| 功能模块 | 具体能力 | 深度讲解章节 |
| --- | --- | --- |
| 设备列表管理 | 设备档案注册、在线状态、统计条、搜索过滤、卡片跳转 | **3.2 设备列表管理** |
| 实时数据接收解析 | 通配符订阅、Topic 路由、解码容错、滑动窗口、实时曲线 | **3.3 实时数据接收与解析** |
| 远程控制 | 下发指令（开关/改阈值/重启）、RPC over MQTT、回执超时 | **3.4 远程控制** |
| 告警 | 设备异常事件、离线推导、告警中心去重与确认 | **3.5 告警与事件** |

这四个功能不是四座孤岛，而是同一条消息流水线上的四个出口：设备列表消费"档案"，曲线消费"遥测"，告警中心消费"事件"，控制面板生产"指令"。理解这一点，后面每一章你都能定位到自己在这条流水线的哪一环。

## 系统架构与数据流向

整套 demo 由两个进程组成：一个 Node 进程跑本地服务端（Broker + 设备模拟器），一个 Vite 进程跑前端开发服务器。两者唯一的交点是 MQTT 协议。

```
        终端 1（Node 进程）                          浏览器（Vite 开发服务器）
┌──────────────────────────────┐            ┌────────────────────────────────────────┐
│  server/simulator.mjs        │            │  IoT Deck（Vue 3 + Pinia）             │
│  8 台模拟设备                 │            │                                        │
│   │ 上行遥测/状态/事件         │  MQTT/TCP  │  下行指令 down/command（QoS 1）         │
│   ▼                          │   :1883    │   ▲                                    │
│  server/broker.mjs (aedes)   │ ─────────► │  MQTT over WebSocket                   │
│   │ 转发到订阅者（含 retain）  │            │  ws://localhost:8083/mqtt              │
│   ▼                          │ ◄───────── │   │                                    │
│  broker 日志（联调观察点）     │  WS :8083  │  连接层 connection.ts → mqtt.js         │
└──────────────────────────────┘   /mqtt    │   ▼                                    │
                                            │  网关层 IotGateway（路由 + 解码容错）    │
                                            │   ▼ handlers 回调                      │
                                            │  状态层 Pinia stores（devices/alerts/   │
                                            │  connection）→ 视图层（列表/详情/告警）  │
                                            └────────────────────────────────────────┘
```

两个端口各司其职：**TCP 1883 是设备侧入口**（真实设备一般走 TCP/TLS，模拟器用原生 mqtt 客户端连接），**WS 8083 路径 `/mqtt` 是前端侧入口**（浏览器无法直接建 TCP 连接，mqtt.js 走 MQTT over WebSocket）。

浏览器内部是一条严格的分层链路，依赖只允许自上而下：

```
视图层      views/DeviceListView · DeviceDetailView · AlertCenterView
  ▲ 读取 computed
状态层      Pinia stores/（devices · alerts · connection）
  ▲ handlers 回调注入
网关层      services/mqtt/index.ts（IotGateway：Topic 路由 + 解码分发 + 指令 RPC）
  ▲
连接层      services/mqtt/connection.ts（退避重连 + 入站看门狗）→ mqtt.js
```

关键设计：**网关层不 import 任何 Pinia store**，依赖通过 `GatewayHandlers` 接口回调注入（见 `src/composables/useIot.ts` 的装配代码）。这让服务层保持无框架依赖——可单测、可搬去非 Vue 环境复用。

## Topic 契约总表

全教程统一使用 `iot/{productId}/{deviceId}/{dir}/{kind}` 四级主题。这是前后端、设备侧共同遵守的"接口契约"，TS 版本定义在 [demo/src/types/iot.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/types/iot.ts)，模拟器侧的发布代码在 [demo/server/simulator.mjs](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/server/simulator.mjs)。

| 主题 | 方向 | QoS | retain | 用途 |
| --- | --- | --- | --- | --- |
| `iot/{p}/{d}/up/telemetry` | 设备 → 云 | 0 | 否 | 遥测数据，高频、可容忍偶发丢失 |
| `iot/{p}/{d}/up/status` | 设备 → 云 | 1 | **是** | 设备档案 + 在线状态，订阅瞬间即收全量 |
| `iot/{p}/{d}/up/event` | 设备 → 云 | 1 | 否 | 异常事件（TEMP_HIGH / BATTERY_LOW / DEVICE_OFFLINE） |
| `iot/{p}/{d}/down/command` | 云 → 设备 | 1 | 否 | 控制指令（switch / setThreshold / reboot） |
| `iot/{p}/{d}/down/command_reply` | 设备 → 云 | 1 | 否 | 指令回执，携带请求 id 关联 |

各主题的 payload 形态（摘自模拟器真实发布代码）：

```jsonc
// 传感器遥测（单包，QoS 0）
{ "mid": "b1c9…", "ts": 1792000000000, "temp": 26.4, "humi": 57.2, "battery": 92, "rssi": -58 }

// 智能插座遥测（单包，QoS 0）：字段集与传感器不同
{ "mid": "7d0e…", "ts": 1792000000000, "power": 1243, "voltage": 221, "on": true }

// 低功耗设备遥测（批量信封，QoS 0）：缓存多个样本一次上报
{ "mid": "9a2f…", "ts": 1792000000000, "samples": [ { "t": 1792000000000, "temp": 25.1, "humi": 55, "battery": 78 } ] }

// 设备档案（QoS 1 + retain）
{ "online": true, "name": "育苗棚 A1 · 温湿度", "product": { "id": "gh01", "name": "温湿度传感器" }, "fw": "v1.4.2", "ip": "192.168.1.20" }

// 离线状态（QoS 1 + retain）
{ "online": false, "reason": "maintenance" }

// 异常事件（QoS 1）
{ "mid": "e4c1…", "ts": 1792000000000, "code": "TEMP_HIGH", "level": "error", "message": "温度 37.2℃ 超过阈值 35℃", "value": 37.2 }

// 控制指令（QoS 1，云 → 设备）
{ "id": "f0a3…", "action": "switch", "params": { "on": false }, "issuedAt": 1792000000000 }

// 指令回执（QoS 1，设备 → 云）
{ "id": "f0a3…", "ok": true, "message": "开关已关闭" }
```

前端只订阅两条通配符主题（定义在 `src/services/mqtt/topics.ts`）：

```ts
// 文件: demo/src/services/mqtt/topics.ts（节选）
/** 前端订阅清单：两级通配符一次拿全部上行 + 指令回执 */
export const SUBSCRIBE_TOPICS = ['iot/+/+/up/#', 'iot/+/+/down/command_reply'] as const
```

为什么是这两条而不是五条？`up/#` 用一级通配符收齐遥测、状态、事件三类上行；指令回执单独订阅；而 `down/command` 是前端自己发出的下行指令，订阅它只会"听到自己的回声"，无需订阅。通配符语义与 QoS 选择依据在 3.3 章展开。

## 环境要求与三步启动

环境要求：

- **Node.js ≥ 20.19 或 ≥ 22**（Vite 8 的硬性要求；本教程实测 v24.17.0）。用 `node -v` 检查，低于要求会直接启动失败；
- **pnpm**（本教程实测 12.10.1）。未安装时执行 `npm install -g pnpm`；
- 浏览器任一现代版本（Chrome/Edge/Safari/Firefox 均可）。

三步启动（在 `demo/` 目录下执行）：

```bash
// 文件: demo/（终端命令，cwd = iot-tutorial-project/demo）
# 第 1 步：安装依赖（生成 node_modules，依据 pnpm-lock.yaml 精确还原）
pnpm install

# 第 2 步：终端 1 —— 启动本地服务端（Broker 1883/8083 + 设备模拟器，一条命令全拉起）
pnpm server

# 第 3 步：终端 2 —— 启动前端开发服务器
pnpm dev
```

> 运行方式：`pnpm install` 后开两个终端，终端 1 执行 `pnpm server`，终端 2 执行 `pnpm dev`，浏览器打开终端 2 输出的地址（默认 `http://localhost:5173`）。

`pnpm server` 成功的标志是终端 1 依次输出：

```text
[broker] TCP 已就绪 mqtt://localhost:1883（设备侧）
[broker] WS  已就绪 ws://localhost:8083/mqtt（前端侧）
[simulator] 8 台设备正在接入 mqtt://localhost:1883
[broker] 接入 +  dev-gh01-001
[device] gh01-001 上线（normal）
…（共 8 台）
[broker] dev-gh01-001 → iot/gh01/gh01-001/up/status (98B, qos1)
```

`pnpm dev` 若遇 5173 被占用（其他 Vite 项目未关），**会自动顺延到 5174、5175…**，以终端实际输出的地址为准，不要想当然访问 5173。单独的 `pnpm broker`（只启 Broker）与 `pnpm devices`（只启模拟器）脚本也存在，日常联调一律用 `pnpm server` 一步到位。停止时在两个终端分别按 `Ctrl+C`。

## 运行与验证

启动完成后，按顺序验证这个**最小闭环**。每一步都标注了对应章节，出问题时可以精准回炉：

- [ ] **① 8 张设备卡片出现**：打开 `http://localhost:5173`（或终端 2 实际地址），列表页应出现 8 张卡片，7 张"在线"、1 张"离线"。原理：设备上线即发布 retained 档案，前端订阅瞬间收齐全部设备清单 → **3.2 章详解**。
- [ ] **② gh01-004 显示离线**："育苗棚 C1 · 温湿度"卡片是灰色离线徽标。原理：模拟器为它发布 retained 的 `status=offline` 后主动断开，保留消息让迟到的订阅者也能看到 → **3.2 章**。
- [ ] **③ 详情曲线滚动**：点击任意在线传感器卡片进入详情，温度/湿度曲线每 800ms 推进，数值持续更新。原理：遥测报文经路由、解码、滑窗入库，图表批量取数 → **3.3 章详解**。
- [ ] **④ 插座开关生效**：进入"泵房 · 智能插座 1"详情，点击开关，约 300ms 后收到"开关已打开"回执，功率曲线从 0 跳到 1200W 左右 → **3.4 章详解**。
- [ ] **⑤ 告警中心有记录**：顶栏告警徽标出现未读计数；进入告警中心能看到温度超限（等尖峰剧本触发）或设备离线记录 → **3.5 章详解**。

同时观察终端 1 的 broker 日志，你会看到持续滚动的消息流（这是后续章节联调时最重要的观察点）：

```text
[broker] dev-gh01-003 → iot/gh01/gh01-003/up/telemetry (95B, qos0)
[broker] dev-pl01-001 → iot/pl01/pl01-001/up/telemetry (72B, qos0)
[broker] dev-gh01-002 批量上报 4 个缓存样本
```

## 最佳实践与常见坑

**坑 1：5173 打不开 / 访问的是"别人的项目"**

- 现象：`pnpm dev` 后浏览器访问 5173，看到的不是 IoT Deck，或完全打不开。
- 原因：5173 被其他 Vite 项目占用，本项目的开发服务器自动顺延到了 5174 等端口；或你的浏览器缓存了旧项目的页面。
- 解法：**以终端 2 实际输出为准**，输出 `Local: http://localhost:5174/` 就访问 5174；顺手用 Ctrl+Shift+R 强刷一次排除缓存。养成"看终端再开浏览器"的习惯，比背端口号可靠。

**坑 2：`pnpm server` 报 `EADDRINUSE`，端口 1883 或 8083 被占**

- 现象：终端 1 报错 `Error: listen EADDRINUSE: address already in use 0.0.0.0:1883`，或前端一直"连接中…"。
- 原因：本机已有一个进程占用了 1883/8083——最常见的是上一次 `pnpm server` 没杀干净，或本机装过 EMQX/Mosquitto 等真实 Broker。
- 解法：先排查占用者并结束它（macOS/Linux 可用 `lsof -i :1883` 找到 PID），再重启。如果是有意共存其他 Broker，可给本项目换端口：复制 `server/broker.mjs` 中的监听端口与 `src/config.ts` 中的 `mqttUrl` 一并修改，**两处必须成对改**。

**坑 3：Node 版本过低，Vite 8 直接拒绝启动**

- 现象：`pnpm dev` 报 `Vite requires Node.js version 20.19+ or 22+...`，或安装依赖阶段就报引擎不兼容。
- 原因：Vite 8 用到了较新的 Node API，老版本 Node（如 18.x）不满足。
- 解法：升级 Node 到 22 LTS 或更高（本教程实测 v24.17.0）。多版本共存需求建议用 nvm/fnm 切换：`nvm install 22 && nvm use 22`，切完重新 `pnpm install`（原生依赖需针对新 Node 重新安装）。

**坑 4：用 npm/yarn 混装导致依赖树错乱**

- 现象：同事/其他教程用 `npm install` 装过一次，之后类型检查大面积报错、版本对不上文档。
- 原因：npm 与 pnpm 的目录结构完全不同（扁平 vs 符号链接），混装会把 `pnpm-lock.yaml` 与实际 `node_modules` 打成两张皮。
- 解法：删除 `node_modules` 后仅用 pnpm 重装：`rm -rf node_modules && pnpm install`。团队协作时把"只许 pnpm"写进 README，并用 `package.json` 的 `packageManager` 字段或 preinstall 钩子强制约束。

## 实操任务

**任务 1：环境自检并记录快照**

在终端执行以下命令，把输出记录到你的学习笔记（后续章节排查问题时，版本快照能省一半时间）：

```bash
// 文件: （终端命令，任意目录）
node -v        # 预期 ≥ v20.19 或 ≥ v22（本教程实测 v24.17.0）
pnpm -v        # 预期 ≥ 9（本教程实测 12.10.1）
```

> 运行方式：直接在终端执行，无需进入项目目录。

**任务 2：验证配置解析链（localStorage 覆盖 Broker 地址）**

项目支持"环境变量 → localStorage 覆盖 → 兜底默认值"三级配置（见 [demo/src/config.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/config.ts)）。在浏览器控制台执行下面一行后刷新页面，再执行 `localStorage.removeItem('iot.mqttUrl')` 恢复：

```js
// 文件: （浏览器 DevTools Console）
localStorage.setItem('iot.mqttUrl', 'ws://localhost:8083/mqtt')
```

> 运行方式：页面打开后按 F12 进入控制台执行，刷新页面。若连接指示器仍为"已连接"，说明 localStorage 覆盖生效且配置链工作正常。

这个实验的价值：让你确认前端到底连向哪里、被谁决定。将来部署到非 localhost 环境（例如局域网 IP 调试手机访问），改的就是这条链路。
