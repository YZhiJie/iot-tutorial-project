## 学习目标

- 掌握一套可复用的端到端验收清单，能独立判断「这个 IoT 监控台是否正常工作」；
- 面对故障能按「现象 → 可能原因 → 定位手段」的结构化思路收敛，而不是盲目试错；
- 熟悉四件调试工具：DevTools WS 帧面板、server 日志对照、网关路由断点、命令行订阅观察；
- 建立「数据流分段定位」的意识：设备 → Broker → 前端，先找断点在哪一段。

## 3.6.1 端到端验收清单

联调验收不是「页面能打开」，而是把系统的每个能力都走一遍。以下 13 条基于本 demo 的设备剧本设计，全部通过才算验收完成。

建议按顺序分组执行：第 1~2 条验「连接与档案」，第 3~5 条验「数据接收」，第 6~7 条验「远程控制」，第 8~9 条验「告警」，第 10~13 条验「容错与恢复」——前面的组失败时，先修好再往下走，否则后面的现象全是噪音。

- [ ] 连接指示器为绿色「已连接」，下方「解析 / 丢弃」计数持续增长（数据在流）
- [ ] 设备列表出现 8 张卡片：gh01-001 ~ gh01-006 + pl01-001 / pl01-002
- [ ] gh01-004 始终显示离线（长期离线剧本：retained status = offline，原因 maintenance）
- [ ] 低功耗设备 gh01-002 的曲线每 15 秒一次跳 4 个点（批量信封剧本），而非连续平滑
- [ ] 进入设备详情，曲线随时间滚动推进，窗口超过 120 点后旧点被裁剪
- [ ] 插座开关：点「关闭插座」→ 日志「成功 · 开关已关闭」→ 功率曲线落到 0W；再打开回执「开关已打开」、功率回到 1200W 附近
- [ ] 重启设备：卡片短暂离线（rebooting）→ 约 2.5s 恢复在线 → 日志「成功 · 设备已完成重启」
- [ ] gh01-003 温度尖峰出现时，全局 error 横幅自动弹出
- [ ] 告警中心按「仅 error」筛选有效；确认处置后未读计数归零、横幅消失
- [ ] 杀掉 `pnpm server` 进程 → 指示器变黄「重连中（第 N 次）」持续递增
- [ ] 重新执行 `pnpm server` → 前端自动恢复连接，8 张卡片档案重新出现，数据继续流动
- [ ] 设备离线或连接断开时，控制面板按钮禁用并显示提示文案
- [ ] 长会话（10 分钟以上）运行后，「解析 / 丢弃」计数趋于平稳，页面操作无明显卡顿（性能粗查）

其中第 10、11 条值得展开：前端重连由 `MqttConnection` 的**全抖动指数退避**驱动（`delay = random(0, min(30s, 1s × 2^attempt))`），所以重连不是等间隔的；恢复依赖模拟器重新接入后**重发 retained 档案**，加上前端重连成功后**显式重订阅**（clean 会话不保留订阅列表）。三者缺一，自动恢复就不成立。

## 3.6.2 故障排查大表

排查 IoT 故障的核心方法是**分段定位**：一条数据从设备到曲线要过三段（设备/模拟器 → Broker → 前端解码与 store），先确认断在哪一段，再查段内细节。下表是本 demo 最常见的八类故障：

| 现象 | 可能原因 | 定位手段 |
| --- | --- | --- |
| 一直「连接中…」或「重连中」 | broker 未启动；MQTT URL 配错；WS 路径不是 /mqtt | Console 找 `[mqtt] 连接错误` 日志；核对 `.env.development` 的 `VITE_MQTT_URL` 与 localStorage 覆盖键 `iot.mqttUrl`；确认 server 日志里 1883/8083 已就绪 |
| 已连接但收不到任何数据 | 订阅通配符写错；两端 Topic 契约不一致 | server 日志看有无 `iot/` 报文发布（有→前端订阅问题，无→设备侧问题）；对照 `SUBSCRIBE_TOPICS` 与模拟器发布主题 |
| 卡片不出现或无档案信息 | retained 档案未发布/被清空（broker 重启且模拟器未重连）；`up/status` 不在订阅范围；档案 JSON 解析失败被丢弃 | 命令行订阅 `iot/+/+/up/status` 看有无保留消息；看「解析/丢弃」计数是否异常增长 |
| 曲线不动 | store 有数据但图表 800ms 定时刷新有延迟感；设备批量稀疏上报（gh01-002 每 15s 4 点）；后台标签页被浏览器节流 | Vue DevTools 看 devices store 的 window 数组是否增长；切回前台观察是否补渲染 |
| 指令总是「超时」 | 设备实际离线；回执主题拼错（两端 `command_reply` 不一致）；模拟器未订阅 `down/command` | server 日志看 `[device] xxx 收到指令`；命令行订阅 `iot/+/+/down/command_reply` 看回执是否发出、载荷是否完整 |
| 回执发出但 Promise 不落定 | id 不匹配：模拟器回执的 id 与请求 id 不一致，pending 查不到被静默丢弃 | server 日志打印了 id 前 8 位（`收到指令 switch (id=xxxx)`），与前端 `onCommandReply` 日志逐条对照 |
| 告警不弹 | 60s 冷却窗口拦截同设备同 code 的后续告警；告警中心级别筛选过滤掉了；warn 不弹横幅（`latestUnackedError` 只认 error，属设计） | 告警中心切「全部级别」；对照时间线确认是否落在冷却窗口内 |
| 重复报文计数持续偏高 | 模拟器刻意制造的 6% 重发剧本（mid 相同，前端应去重）——这是**预期行为** | 观察丢弃计数增长但曲线无重复毛刺，说明 codec 去重生效，无需处理 |
| 频繁掉线重连（重连风暴） | clientId 冲突互踢（MQTT 规定同 id 后连踢前连）；重连退避未随机化，服务端重启后全体客户端同时冲击 | broker 日志看同一 clientId 反复「接入 + / 断开 -」；确认 clientId 含随机后缀、退避用全抖动（对照 `connection.ts`） |

读这张表的方法：先锁定**最精确的现象**（越具体越好，「曲线不动」不如「gh01-002 曲线不动」好定位），再从上往下排除原因，每一项都用**可观测的手段**证实或证伪，而不是改一行代码碰运气。

### 排查示范：一次「指令超时」的完整动线

空谈不如走一遍。假设现象是：对 pl01-001 点「打开插座」，指令日志 8 秒后显示「超时」。按分段定位的思路走：

**第 1 步：确定断点在哪一段。** 三处证据依次取：

- 浏览器 WS 帧面板 → 有没有 `down/command` 的**出站**帧？（有 → 前端已发出；没有 → 查前端，比如连接状态不对）
- server 终端 → broker 日志里有没有对应的转发记录？（broker 收到才会打印）
- server 终端 → `[device] pl01-001 收到指令 switch (id=xxxx)` 在不在？

```text
[broker] web-console_a1b2c3d4 → iot/pl01/pl01-001/down/command (58B, qos1)   ← broker 收到并转发
（缺：[device] pl01-001 收到指令 …）                                          ← 设备侧没收到/没处理
```

**第 2 步：段内定位。** 断点在「模拟器收报文」这一段。可能原因按排查表：设备离线？——不是，卡片在线；订阅丢了？——模拟器只在 connect 回调里订阅一次，若它重连过且订阅失败就会哑掉。看 server 日志里模拟器最近的「接入 + / 断开 -」记录即可证实。

**第 3 步：修复与回归。** 重启 `pnpm server` 让模拟器重新接入订阅，重发指令验证回执正常，最后把这次故障的「现象 / 根因 / 修法」记进团队的排查文档。

注意整条动线没有一行「猜」的成分：每一跳都有日志或帧证据。养成这个习惯，联调效率会比「改一版试一下」高一个数量级。

### 附：Console 报错文本速查

前端日志里的关键报错文本都是代码里写死的，可以直接反查出处：

| Console 报错 | 出处与含义 |
| --- | --- |
| `WebSocket connection to 'ws://localhost:8083/mqtt' failed` | 连不上 Broker：进程没起、端口错、或路径不是 /mqtt |
| `[mqtt] 连接错误：…` | mqtt.js 的 error 事件（connection.ts 打印）；它之后通常紧跟 close，真正原因常要看 broker 日志 |
| `[mqtt] 订阅失败` | subscribe 回调返回 err：重订阅没成功，此刻连接虽在但收不到数据 |
| `[device] xxx 指令解析失败` | 模拟器侧：收到的指令载荷不是合法 JSON 或字段缺失 |
| `[gateway] 指令回执 {…}` | useIot 里保留的全局回执日志：核对 id 与 ok 字段就靠它 |
| `IoT 网关尚未启动` | getGateway 在 start() 之前被调用——装配时序问题，查调用时机 |

另有一个不是报错但最常见的「静默失败」：什么都没打印、数据也不来——那是 `parseTopic` 返回 null 后 `route` 静默 return 了。遇到「无日志、无数据」，第一反应就应该是主题没匹配上契约。

## 3.6.3 调试工具箱

**工具一：DevTools 的 WS 帧面板。**
Network 面板过滤 WS → 选中 `ws://localhost:8083/mqtt` 连接 → Messages/Frames 标签。这里能看到前端收发的**每一条 MQTT 报文的原始帧**，按时间排序、可看载荷方向。判断「前端到底收没收到某条消息」，这里是最终事实。

**工具二：server 日志逐条对照。**
`pnpm server` 的终端里，Broker 会打印每条 iot 报文的发布记录：

```text
[broker] web-console_a1b2c3d4 → iot/pl01/pl01-001/down/command (58B, qos1)
[broker] dev-pl01-001 → iot/pl01/pl01-001/up/event (96B, qos1)
[device] pl01-001 收到指令 switch (id=9f2e4a10)
```

> 运行方式：`pnpm server` 启动后自动输出，联调时保持终端可见。

对照法：前端「发了指令」→ 找 broker 日志里对应的 down/command 行 → 找 device 日志「收到指令」→ 找回执的 up 报文。四步哪步断了，断点就在哪。

**工具三：在 route 打断点。**
`IotGateway.route` 是所有上行报文的必经之路：

```ts
// 文件: demo/src/services/mqtt/index.ts
private route(topic: string, payload: Uint8Array): void {
  const info = parseTopic(topic)
  if (!info) return // ← 断点打这里：契约不匹配的报文会在这里静默消失
  // ……
}
```

> 运行方式：在浏览器 DevTools 的 Sources 面板中定位该文件打断点，或直接用 `debugger` 语句临时插入。

两个高价值断点：`if (!info) return` 抓「主题不在契约内被静默忽略」的报文；`command_reply` 分支抓回执内容与 id。注意**静默失败是 IoT 前端最大的敌人**——很多「数据消失」最终都停在类似的 return 上。

**工具四：mosquitto_sub 命令行观察（可选安装）。**
绕过前端，直接以第三方客户端身份订阅全局：

```bash
# 终端命令（需安装 mosquitto 客户端工具，如 brew install mosquitto）
mosquitto_sub -h localhost -p 1883 -t 'iot/#' -v
```

> 运行方式：在另一终端执行，实时打印所有 iot 报文的「主题 + 载荷」。

它的价值是**独立于前后端**的第三方视角：怀疑模拟器没发、怀疑前端订阅错、想看回执原始载荷，它都给得出不经加工的答案。`-v` 会连主题一起打印，排查主题级问题时必备。

**工具五：解码统计计数器。**
`codec.ts` 导出了一个响应式的统计单例，连接指示器底部实时展示「解析 / 丢弃」，它自己还细分了两类丢弃原因：

```ts
// 文件: demo/src/services/mqtt/codec.ts
/** 解码统计（模块级单例，UI 直接引用展示：ConnectionIndicator 底部） */
export const codecStats = reactive({
  received: 0, // 收到上行报文总数
  decoded: 0, // 成功解码
  dropped: 0, // 丢弃总数
  duplicates: 0, // 其中：重复报文
  corrected: 0, // 其中：时钟漂移被钳制的报文
})
```

> 运行方式：该文件已随 demo 提供，无需单独运行。

判读口诀：`dropped` 增长且 `duplicates` 同步增长 → 是 6% 重发剧本，正常；`dropped` 增长但 `duplicates` 不动 → 真有报文解码失败，去查载荷；`corrected` 增长 → 低功耗设备的时钟偏移被钳制（90s 在容忍内时不会触发，超出 5 分钟才会）。

## 3.6.4 性能粗查

IoT 监控台是长会话应用，性能问题往往是「开一小时后变卡」型的。开发阶段就做一次粗查，操作与判读各三步：

操作步骤：

1. DevTools → Performance 面板 → 点录制 → 正常操作页面 10 秒（切详情、开合插座、看告警）→ 停止录制；
2. 顶栏看 FPS 轨道与主线程火焰图，展开 Bottom-Up 视图按 Total Time 排序；
3. Memory 面板录制前后各拍一次堆快照，用 Summary 视图对比对象总数。

判读要点：

- 主线程有没有 **Long Task**（超过 50ms 的任务块）。本 demo 的负载量级（8 台设备、3~15s 一报、图表 800ms 一刷）不应出现明显长任务；
- 若有，优先怀疑两处：ECharts `setOption` 的数据量（滑窗 120 点是刻意设的上限，别在演示时随手调到 10000）与对大数组的深层响应式 watch；
- 堆快照对比确认长会话没有持续增长——滑窗裁剪、告警 200 条上限、指令日志 20 条上限都是为此设计的，快照前后差值应稳定在一个小范围内。

## 运行与验证

```bash
# 终端命令（在 demo 目录执行）
pnpm server   # 终端 1：Broker + 8 台模拟设备
pnpm dev      # 终端 2：前端控制台
```

> 运行方式：浏览器打开 vite 输出的地址（默认 localhost:5173）。

重点走查「断电恢复」这条链路（对应验收清单第 10、11 条）：

1. 在 `pnpm server` 终端按 Ctrl+C 杀掉进程 → 前端指示器变黄「重连中（第 N 次）」，次数按退避节奏递增（全抖动随机，间隔不均匀是正常的）；
2. 重新执行 `pnpm server` → broker 就绪 → 模拟器 800ms 后接入并重发 retained 档案 → 前端下一次重连尝试成功并显式重订阅 → 指示器变绿，8 张卡片档案恢复，曲线断流后续接。
3. 全程对照 server 终端日志，你会看到完整的恢复动线：

```text
[broker] TCP 已就绪 mqtt://localhost:1883（设备侧）
[broker] WS  已就绪 ws://localhost:8083/mqtt（前端侧）
[broker] 接入 +  dev-gh01-001
[broker] dev-gh01-001 → iot/gh01/gh01-001/up/status (…)   ← retained 档案重发
[broker] 接入 +  web-console_xxxxxxxx                      ← 前端重连成功
```

> 运行方式：`pnpm server` 启动后自动输出，对照浏览器指示器状态变化逐行确认。

把这条动线记熟：以后任何「重启服务端后前端没恢复」的问题，都能按「broker 就绪 → 设备接入 → 档案重发 → 前端接入」四步逐级检查缺了哪环。

## 最佳实践与常见坑

**坑 1：改了契约只改一端。**
现象：某类报文「无声消失」——无报错、无警告，曲线/告警/回执就是不来。
原因：主题或字段只改了前端或只改了模拟器，`parseTopic` 正则不匹配返回 null，`route` 里 `if (!info) return` 静默忽略；或字段类型对不上被 codec 丢弃并计入「丢弃」计数。
解法：契约的单一事实来源收拢在 `types/iot.ts` + `topics.ts`（注释即契约文档），两端改动必须同批提交；用 mosquitto_sub 对照真实主题；改完跑一遍 3.6.1 的验收清单。

**坑 2：把排查寄托在刷新页面。**
现象：出问题就 F5，「好了」，过一会儿又坏；根因永远找不到。
原因：刷新会重建全部 store、清空 codec 统计与 pending 指令、重放 retained 档案——它一次性「洗掉」了几乎所有现场，偶发的时序问题被掩盖而非修复。
解法：先取证再动手。Console 报错、WS 帧面板、server 日志三处证据拿全，至少确定断点在哪一段，才允许动页面。

**坑 3：只盯浏览器日志，不查服务端。**
现象：在前端反复打断点、加日志，毫无头绪。
原因：MQTT 链路是设备 → Broker → 前端三段，前端只能看到「到达自己」的部分；报文根本没发出来、或 Broker 没转发到位，前端再怎么查也是空。
解法：先分段。mosquitto_sub 或 broker 日志确认报文是否存在，再决定查上游还是下游。

## 实操任务

**人为制造一个故障：改错订阅通配符，再用排查表把它找回来。**

步骤：

1. 打开 `src/services/mqtt/topics.ts`，把订阅清单改成只订阅遥测：

```ts
// 文件: demo/src/services/mqtt/topics.ts（故意改错，练完请恢复）
export const SUBSCRIBE_TOPICS = ['iot/+/+/up/telemetry'] as const
```
