## 3.5.1 告警的三路来源

`AlertItem` 是告警中心的统一记录格式，所有来源最终都汇入 `alerts.push()`。三路来源分别是：

**来源 A：设备事件（up/event → decodeEvent → pushEvent）。**
设备固件自己检测到异常（温度超阈值、电量低），主动上报事件报文。链路：`IotGateway.route` 的 `event` 分支 → `decodeEvent` 做容错解码（level 非法兜底为 info、缺 message 兜底为占位文案）→ 回调 `handlers.onEvent` → 装配层转交告警 store：

```ts
// 文件: demo/src/composables/useIot.ts
onEvent: (deviceId, productId, ev) => {
  alerts.pushEvent(deviceId, devices.nameOf(deviceId, productId), ev)
},
```

> 运行方式：该文件已随 demo 提供，`pnpm dev` 启动后自动生效。

`pushEvent` 会把事件附带的 `value` 拼进文案（「温度 38.2℃ 超过阈值 35℃（当前值 38.2）」），处置时不用再回详情页查值。

在进入 store 之前，事件报文先经过解码层的容错清洗——设备固件是不可信的对端，字段可能缺失、级别可能乱填：

```ts
// 文件: demo/src/services/mqtt/codec.ts
/** 异常事件（up/event）：字段宽松兜底，绝不让坏事件炸掉告警中心 */
export function decodeEvent(payload: unknown, recvTs: number): DecodeResult<DeviceEvent> {
  codecStats.received++
  const parsed = parseJson(text(payload))
  if (!parsed.ok) {
    codecStats.dropped++
    return parsed
  }
  const obj = parsed.value
  const level = obj.level === 'warn' || obj.level === 'error' || obj.level === 'info' ? obj.level : 'info'
  codecStats.decoded++
  return {
    ok: true,
    value: {
      ts: fixTs(obj.ts, recvTs).ts,
      code: typeof obj.code === 'string' ? obj.code : 'UNKNOWN',
      level,
      message: typeof obj.message === 'string' ? obj.message : '(设备未提供描述)',
      value: num(obj.value),
    },
  }
}
```

> 运行方式：该文件已随 demo 提供，无需单独运行。

三个兜底都值得记住：level 非法值降为 `info`（绝不因脏数据抛错）、code 缺失兜底为 `UNKNOWN`、message 缺失给占位文案。告警中心因此永远不会因为一条烂报文而白屏。

**来源 B：前端本地推导（离线看门狗）。**
有些故障设备自己报不出来——半死不活、静默失联。devices store 里每 5 秒跑一次看门狗：某设备 `lastSeenAt` 距今超过 `CONFIG.offlineAfterMs`（45 秒）仍在线，就判定离线并推一条告警：

```ts
// 文件: demo/src/stores/devices.ts
function setOnline(e: DeviceEntry, online: boolean, reason?: string): void {
  const was = e.online
  e.online = online
  if (online) {
    e.offlineAlerted = false
    e.lastSeenAt = Date.now()
    return
  }
  if (was && !e.offlineAlerted) {
    e.offlineAlerted = true
    useAlertsStore().push({
      deviceId: e.profile?.deviceId ?? '?',
      deviceName: e.profile?.name ?? e.profile?.deviceId ?? '?',
      level: 'warn',
      code: 'DEVICE_OFFLINE',
      message: `设备离线${reason ? `（${reason}）` : ''}`,
      fromDevice: false,
    })
  }
}
```

> 运行方式：该文件已随 demo 提供，无需单独运行。

注意离线告警其实有**两条触发路径**：设备发了 retained 的 `up/status online:false` 时走 `ingestProfile → setOnline` 立即告警；status 报文丢失时由 45s 看门狗兜底。`offlineAlerted` 标记保证同一次离线只报一次，恢复在线时复位。`fromDevice: false` 就是展示层「前端推导」标注的数据来源。

**来源 C：平台规则引擎推送（扩展接口）。**
真实平台通常有一个规则引擎：遥测流入 → 按规则（如「温度连续 3 次超阈值」）判定 → 生成告警推送。本 demo 未启用，但 `push()` 的入参结构对它保持兼容——将来接入时只需在别处调用 `alerts.push()`，展示层零改动。

## 3.5.2 alerts store：冷却去重、容量上限与确认处置

```ts
// 文件: demo/src/stores/alerts.ts
const CAP = 200
const DEDUPE_WINDOW_MS = 60_000

function push(input: PushInput): void {
  const key = `${input.deviceId}:${input.code}`
  const now = Date.now()
  const last = lastByKey.get(key)
  if (last !== undefined && now - last < DEDUPE_WINDOW_MS) return
  lastByKey.set(key, now)

  const item: AlertItem = {
    id: `a_${++seq}_${now.toString(36)}`,
    ts: input.ts ?? now,
    deviceId: input.deviceId,
    deviceName: input.deviceName,
    level: input.level,
    code: input.code,
    message: input.message,
    fromDevice: input.fromDevice,
    acked: false,
  }
  list.value.unshift(item) // 新告警置顶
  if (list.value.length > CAP) list.value.pop()
}
```

> 运行方式：该文件已随 demo 提供；`pnpm dev` 后打开「告警中心」页面即可观察。

记录结构本身也说明了设计意图——`AlertItem` 全部是**值拷贝的快照字段**，没有任何指向设备对象的引用：

```ts
// 文件: demo/src/types/iot.ts
/** 告警中心的一行记录（三路来源，见 stores/alerts.ts） */
export interface AlertItem {
  id: string
  ts: number
  deviceId: string
  deviceName: string
  level: EventLevel
  code: string
  message: string
  /** true=设备上报事件；false=前端本地推导（如离线看门狗） */
  fromDevice: boolean
  acked: boolean
}
```

> 运行方式：类型定义已随 demo 项目提供，无需单独运行。

四个设计逐一说明：

- **冷却去重**：key 是 `deviceId:code`，60 秒窗口内同设备同类型告警只收第一条。没有它，gh01-003 每 4~8 秒一次、25% 概率的温度尖峰会让告警中心每分钟多出十几条重复记录——这就是「告警风暴」。注意窗口记录的是**最后一条的时间**，所以风暴结束后 60 秒，下一轮告警能正常进来，不会永久屏蔽。
- **容量上限 200 条**：`unshift` 置顶 + 超限 `pop` 淘汰最旧。告警是低频数据，200 条足够回溯，长会话内存恒定。
- **两个派生值**：`unreadCount`（未确认数，侧边栏角标 / 顶部按钮禁用逻辑用）和 `latestUnackedError`（最新一条未确认的 error，全局横幅的数据源）都是 computed，从 `list` 自动派生，不存在第二份需要同步的状态。
- **确认处置**：`ack(id)` 单条确认，`ackAll()` 全部确认。告警不是日志——它带 `acked` 状态，代表「有人看过并处理了」；未确认的 error 才有资格弹横幅，避免已处置的问题反复打扰。

## 3.5.3 展示层三件套与级别语义

同一份告警数据，三个视图各取所需：

**告警中心 AlertCenterView：全量 + 筛选 + 处置。**

```vue
<!-- 文件: demo/src/views/AlertCenterView.vue -->
<select v-model="levelFilter" class="input select">
  <option value="all">全部级别</option>
  <option value="error">仅 error</option>
  <option value="warn">仅 warn</option>

</select>
<button class="btn" :disabled="alerts.unreadCount === 0" @click="alerts.ackAll()">
  全部确认
</button>
<!-- 每行：级别标签 + 设备名 + code + 来源标注 + 消息 + 相对时间 + 确认按钮 -->
<span class="alert-src">{{ a.fromDevice ? '设备上报' : '前端推导' }}</span>
```

> 运行方式：该文件已随 demo 提供；`pnpm dev` 后进入「告警中心」页面。

级别筛选是纯前端 computed 过滤；「全部确认」按钮在未读为 0 时禁用；每条记录都标注来源（设备上报 / 前端推导）——处置时你能立刻分清「设备自己发现的」和「平台推断的」。相对时间用 5 秒一次的定时器刷新，避免「刚刚」永远停在那里。

**全局横幅 AlertBanner：最新 error 的强提醒。**

```vue
<!-- 文件: demo/src/components/AlertBanner.vue -->
<transition name="banner">
  <div v-if="latest" class="alert-banner">
    <span class="banner-dot" />
    <div class="banner-body">
      <div class="banner-title">{{ latest.deviceName }} · {{ latest.code }}</div>
      <div class="banner-msg">{{ latest.message }}</div>
    </div>
    <button class="btn btn-ghost btn-sm" @click="goDetail">查看</button>
    <button class="btn btn-ghost btn-sm" @click="alerts.ack(latest.id)">知道了</button>
  </div>
</transition>
```

> 运行方式：该文件已随 demo 提供，横幅挂在 App 布局顶层，任何页面触发 error 都会弹出。

数据源就是 `latestUnackedError` computed：没有任何轮询，error 一进 store 横幅自动滑入（`transition` 0.25s 位移 + 透明度动画），ack 之后自动滑出或切换到下一条未确认 error。「查看」跳详情页并顺手 ack——用户已经去处置了，横幅没必要再占着屏幕。


处置告警时最常问「这台设备最近还发生了什么」，在这里一眼可见。

**级别语义与颜色映射。** 三级事件在各视图用统一的配色语言：`info`（蓝色，accent 色）——计划内通知，如「设备计划内停机」；`warn`（黄色）——需要关注但未失控，如设备离线推导、电池低；`error`（红色）——必须立即处置，如温度超阈值，也是唯一会弹全局横幅的级别。CSS 类名约定为 `level-info / level-warn / level-error`，两个视图重复定义了一遍——小项目可以接受，规模大了值得抽成共享样式。

## 3.5.4 告警风暴抑制的进阶讨论

本 demo 用的是最简单的**冷却窗口**。真实系统里还有两档策略，各有适用场景：

- **冷却窗口（本 demo）**：同 key 60s 只收一条。实现最简单，代价是窗口内的**状态变化被吞**——比如温度在 60s 内先超阈又恢复又超阈，你只会看到一条。适合事件频率高、单条信息量大的场景。
- **聚合**：窗口内不丢弃而是合并——同 key 的后续事件只给计数器 +1、更新最后消息，UI 显示「TEMP_HIGH ×7（最近 38.9℃）」。信息零丢失，但告警对象从「一条记录」变成「一条记录 + 计数」，排序与 ack 语义都要跟着改。
- **静默期 / 升级**：运维手段。对已知噪音（某设备某 code）手动设置静默期；反过来，同一 error 连续 N 个窗口未恢复则升级为更高级别或外发通知（短信/电话）。解决的是「告警疲劳」——人对重复告警会脱敏。

三者的选择取决于告警的价值密度：demo 里告警稀疏且有剧本，冷却窗口够了；设备上千、规则上百的平台，通常三者并存。

验证两条剧本链路：

1. **温度尖峰（来源 A）**：停留在任意页面等待 gh01-003 的尖峰（每 4~8s 一报、25% 概率，通常一两分钟内出现）→ 右下角横幅滑入「育苗棚 B1 · 温湿度 · TEMP_HIGH」→ 告警中心出现 error 记录（来源标注「设备上报」，文案带当前值）→ 进入 gh01-003 详情，「最近事件」面板同步出现同一条。三处数据同源，应完全一致。
2. **计划内下线（来源 B）**：观察 gh01-006，启动约 40s 后模拟器发布 retained 离线状态 → 卡片变灰，告警中心出现 warn「设备离线（graceful_shutdown）」，**来源标注「前端推导」**。设备其实同时上报了一条 info 级「设备计划内停机」事件，但与 warn 同设备同 code，被 60s 冷却合并——想一想：这是预期行为还是信息损失？如果要两者都保留，key 应该怎么设计？
3. **确认处置**：告警中心点单条「确认」→ 行变半透明、未读数减一；「全部确认」后横幅消失。

## 最佳实践与常见坑

**坑 1：告警无去重，风暴刷屏。**
现象：告警中心每分钟多出十几条 TEMP_HIGH，真正的新告警被淹没，未读数失去意义。
原因：`push` 不设防，设备高频事件（或规则引擎误配）直接打爆列表。
解法：`deviceId:code` 冷却窗口（本 demo 60s）；更复杂的场景再上聚合计数。注意去重 key 不能只用 code——不同设备的同类告警必须都能进来。

**坑 2：告警对象直接存设备对象引用，状态串改。**
现象：历史告警里的设备名/状态「自己变了」，已确认的记录莫名其妙显示最新遥测值。
原因：push 时存了 `DeviceEntry` 的响应式引用而非快照——设备后续的任何 mutation 都会「穿透」到历史告警上。
解法：push 时拍快照：`AlertItem` 只存 `deviceId`、`deviceName` 字符串等值拷贝字段（本 demo 即如此）。告警是「发生时刻的事实记录」，必须是不可变快照。

**坑 3：error 横幅遮住操作按钮。**
现象：详情页弹横幅后，「重启设备」「设置阈值」按钮点不到——横幅 fixed 定位在右下角、宽 380px、z-index 100，小屏幕上正好压在控制面板上。
原因：全局浮层没有给内容区让位。
解法：给主内容区预留底部空间（横幅可见时加 padding-bottom）；或横幅支持手动收起；或把横幅放到导航栏一侧，不覆盖操作区。核心原则：**提醒不能阻断处置动作**。

## 实操任务

**新增「电池低」前端告警规则——给来源 C（平台侧规则）写一个雏形。**

gh01-005 的电量持续衰减（初始 78%，每次上报 -0.6%），设备端跌破 20% 时会自报 BATTERY_LOW。你的任务是在**前端**独立实现同类规则，模拟真实平台「规则引擎」的角色。

步骤提示（4 步）：

1. `src/stores/devices.ts`：仿照 `offlineAlerted`，给 `DeviceEntry` 加一个 `lowBatteryAlerted` 标记字段；
2. 在 `ingestTelemetry` 末尾检查最后一点：`battery` 存在且 `< 20`、且未告警过 → 调用 `useAlertsStore().push({ deviceId, deviceName: e.profile?.name ?? deviceId, level: 'warn', code: 'BATTERY_LOW_FRONTEND', message: `电量 ${battery}%，低于 20%（前端规则）`, fromDevice: false })`，并置位标记；
3. 电量恢复 `>= 20` 时复位标记（仿照 `setOnline` 对 `offlineAlerted` 的处理）；
4. 验证：gh01-005 约 6~7 分钟跌破 20%（想加速可临时把模拟器初始 battery 改成 25）。注意前端规则的 code 与设备自报的 `BATTERY_LOW` 不同，所以两条都会出现——这正是「设备自检 + 平台规则」双保险的雏形；如果产品上只想保留一条，你会怎么取舍？

> 运行方式：改完保存，vite 热更新自动生效；等待或加速电池衰减后，在告警中心筛选 warn 观察两条 BATTERY_LOW 类记录的来源标注差异。
