曲线滚动是监控台的"心跳"。但要让它可信，中间隔着整整一条流水线：字节流从 Broker 出发，穿越 WebSocket、mqtt.js 事件、Topic 路由、解码容错、滑窗入库，最后才被图表消费。本章沿一条真实遥测走完全程——读懂它，你就掌握了前端接入 MQTT 数据流的完整骨架。

## 学习目标

- 能逐环节说清一条遥测从 Broker 到曲线的旅程，并指出每一环节的容错责任；
- 掌握 `+` 与 `#` 通配符语义，理解前端订阅清单为何是那两条、为何不订阅 `down/command`；
- 建立 QoS 选择策略的判断力：哪些消息配 QoS 1，哪些 QoS 0 就够；
- 理解解码层的四道工序（JSON 解析、mid 去重、时钟漂移钳制、字段校验）与批量信封展开；
- 学会用"断点观察法"亲手追踪消息流。

## 一条遥测的完整旅程

先看全景。以传感器 gh01-001 的一条温度遥测为例：

```
 设备模拟器（server/simulator.mjs）
   reportSensor() → publish('iot/gh01/gh01-001/up/telemetry', payload)
        │
        ▼  TCP 1883
 ┌──────────────────────────────┐
 │ aedes Broker                 │  按订阅关系转发给所有匹配订阅者
 └──────────────────────────────┘
        │
        ▼  WebSocket 8083（路径 /mqtt）
 浏览器：mqtt.js 客户端触发 'message' 事件            （connection.ts）
        │
        ▼
 IotGateway.route(topic, payload)                    （services/mqtt/index.ts）
   ├─ parseTopic(topic) → 不认识的主题？return 静默忽略
   └─ kind === 'telemetry' → decodeTelemetry(payload, recvTs)   （codec.ts）
        ├─ JSON 解析失败 ──────────────→ dropped++ 并终止
        ├─ mid 重复（去重命中）────────→ dropped++ 并终止
        ├─ 批量信封？展开 samples 为多个遥测点
        └─ 逐样本：字段校验、时间戳漂移钳制 → TelemetryPoint[]
        │
        ▼  handlers.onTelemetry（useIot.ts 装配时注入）
 devices store.ingestTelemetry(deviceId, productId, points)     （stores/devices.ts）
        ├─ ensure(deviceId)（档案未到也兜底建项、推导在线）
        ├─ points 逐个 push 进 e.window（滑窗）
        └─ 超出 windowCap=120 → splice 裁掉最旧
        │
        ▼  消息侧工作结束（此处与 UI 解耦）
 TelemetryChart：每 800ms 定时从滑窗批量取数 → setOption  （TelemetryChart.vue）
```

逐环节贴码。第一环，连接层把 mqtt.js 的原始事件转交出去，自己只维护"最后入站时间"（供假死看门狗用）：

```ts
// 文件: demo/src/services/mqtt/connection.ts（节选）
this.client.on('message', (topic, payload) => {
  this.lastInboundAt = Date.now()
  this.events.onMessage(topic, payload)
})
```

第二环，网关路由。`parseTopic` 用白名单正则把字符串主题变成结构化对象，不认识的主题返回 `null`，路由直接静默忽略——这是边界防御的第一道闸：

```ts
// 文件: demo/src/services/mqtt/topics.ts（节选）
const TOPIC_RE = /^iot\/([^/]+)\/([^/]+)\/(up|down)\/(telemetry|status|event|command|command_reply)$/

/** 解析 Topic 为结构化信息；不属于本契约的主题返回 null（调用方静默忽略） */
export function parseTopic(topic: string): TopicInfo | null {
  const m = TOPIC_RE.exec(topic)
  if (!m) return null
  return {
    productId: m[1] as string,
    deviceId: m[2] as string,
    dir: m[3] as 'up' | 'down',
    kind: m[4] as TopicInfo['kind'],
  }
}
```

```ts
// 文件: demo/src/services/mqtt/index.ts（节选）
/** 消息路由：Topic 解析 → 按类型分发解码 → 交回 handlers */
private route(topic: string, payload: Uint8Array): void {
  const info = parseTopic(topic)
  // 不属于本契约的主题（其它应用/心跳包等）：静默忽略
  if (!info) return
  const recvTs = Date.now()

  switch (info.kind) {
    case 'telemetry': {
      const r = decodeTelemetry(payload, recvTs)
      if (r.ok) this.handlers.onTelemetry(info.deviceId, info.productId, r.value)
      break
    }
    // … status / event / command_reply 各自分发，见源码
  }
}
```

第三环，解码层把"不可信的字节流"变成"可信的领域对象"，这是整条流水线容错最密集的地方（下一节细讲）。第四环，store 入库——注意 `lastSeenAt` 用**本地接收时刻**而非设备时间戳，天然免疫设备时钟漂移：

```ts
// 文件: demo/src/stores/devices.ts（节选）
function ingestTelemetry(deviceId: string, _productId: string, points: TelemetryPoint[]): void {
  if (points.length === 0) return
  const e = ensure(deviceId)
  if (!e.online) {
    e.online = true
    e.offlineAlerted = false
  }
  // lastSeen 用本地接收时刻：设备时钟可能漂移，不能信它的时间戳
  e.lastSeenAt = Date.now()

  for (const p of points) e.window.push(p)
  const last = points[points.length - 1]
  if (last) e.latest = last
  const onPoint = points.find((p) => typeof p.on === 'boolean')
  if (onPoint && onPoint.on !== undefined) e.on = onPoint.on

  // 滑窗裁剪：一次性删除超出上限的最旧数据（splice 比循环 shift 高效）
  if (e.window.length > CONFIG.windowCap) {
    e.window.splice(0, e.window.length - CONFIG.windowCap)
  }
}
```

第五环是本章的"反直觉担当"——图表**不订阅消息、不做 watch，而是每 800ms 轮询滑窗**：

```ts
// 文件: demo/src/components/TelemetryChart.vue（节选）
function render(): void {
  const e = entry.value
  if (!ensure()) return
  const win = e?.window ?? []
  const series = seriesDef.value.map((s) => ({
    name: s.name,
    type: 'line',
    showSymbol: false,
    smooth: true,
    data: win.map((p) => [p.ts, p[s.key] ?? null]),
    lineStyle: { color: s.color, width: 1.5 },
    itemStyle: { color: s.color },
    // … 传感器温度序列附带阈值 markLine，见源码
  }))

  setOption(
    { /* 坐标轴/图例等静态配置 */ series },
    { notMerge: true },

let timer: ReturnType<typeof setInterval> | null = null

  render()
  timer = setInterval(render, 800)
})
onUnmounted(() => {
  if (timer) clearInterval(timer)
})
```

为什么轮询而不是"来一条画一条"？8 台设备秒级上报，如果每条消息都触发一次 ECharts `setOption`，图表帧率被消息节奏绑架，消息越密集页面越卡。**800ms 批量取数把"每秒 N 条消息"与"图表帧率"解耦**：消息频率涨十倍，图表渲染成本不变。`notMerge: true` 保证切换设备时旧序列不残留。

## 通配符订阅与 QoS 策略

前端只订阅两条主题，一次性覆盖全部数据面：

```ts
// 文件: demo/src/services/mqtt/topics.ts（节选）
/**
 * 前端订阅清单：两级通配符一次拿全部上行 + 指令回执
 * `#` 匹配剩余全部层级；`+` 匹配单层
 */
export const SUBSCRIBE_TOPICS = ['iot/+/+/up/#', 'iot/+/+/down/command_reply'] as const
```

两条通配符的语义拆解：

- **`+` 匹配恰好一层**。`iot/+/+/up/#` 中两个 `+` 依次吃掉 productId、deviceId——任何产品、任何设备的上行都命中。若某天只想听传感器，改成 `iot/gh01/+/up/#` 即可，订阅粒度随主题层级自由缩放；
- **`#` 匹配剩余全部层级（必须放末尾）**。`up/#` 同时命中 `up/telemetry`、`up/status`、`up/event` 三类消息，一条订阅搞定三类数据；
- **为什么没有 `#` 打底的 `iot/#`**？那会把 `down/command` 也收进来。下行指令是**前端自己发出的**，订阅它只会"听到自己的回声"——除了浪费流量，还会诱导新手在路由里误处理下行消息。源码注释给出了答案：下行指令的审计通常另设专用通道，教学项目从简，前端只关心回执。

QoS 的选择不是"越高越好"，而是**按消息的丢失代价与频率权衡**：

| 消息类型 | QoS | retain | 理由 |
| --- | --- | --- | --- |
| `up/telemetry` 遥测 | 0 | 否 | 高频（8 台设备 3~8 秒一条），单条丢失曲线无感知；QoS 1 的确认重传开销与重复报文处理成本不值得 |
| `up/status` 档案状态 | 1 | 是 | 低频但关键，丢失会造成"幽灵设备/幽灵离线"；retain 保证订阅瞬间收全量 |
| `up/event` 异常事件 | 1 | 否 | 告警不可丢；QoS 1 的"至少一次"可能重复，交给 codec 的 mid 去重兜底 |
| `down/command` 指令 | 1 | 否 | 用户点击必须有下文；配合回执超时机制（`CONFIG.commandTimeoutMs`）形成 RPC |
| `down/command_reply` 回执 | 1 | 否 | 丢失会让前端白等到超时；网关按 id 关联，迟到回执幂等忽略 |

一个容易忽略的组合拳：**QoS 1 的"至少一次"意味着可能重复**，而 MQTT 协议层不帮你去重——去重的责任被明确分配给了 codec 的 `markSeen`。分层思考：传输层保证"到"，解码层保证"对"。

## 解码层：批量信封、去重与时钟漂移

模拟器刻意埋了两类脏数据（见 [demo/server/simulator.mjs](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/server/simulator.mjs) 注释）：约 6% 概率原样重发上一条遥测（mid 相同）、低功耗设备的批量样本带 90 秒时钟偏移。解码层 [demo/src/services/mqtt/codec.ts](https://github.com/YZhiJie/iot-tutorial-project/blob/main/demo/src/services/mqtt/codec.ts) 的职责就是消化它们。先看两个基础工件：

```ts
// 文件: demo/src/services/mqtt/codec.ts（节选）
/** 时间戳漂移容忍：偏差超过 5 分钟视为设备时钟异常，钳制为本地接收时间 */
const MAX_TS_DRIFT_MS = 5 * 60 * 1000
/** 去重窗口：保留最近 500 个报文 id（环形淘汰） */
const DEDUPE_CAP = 500

/** 首次出现返回 true；已见过返回 false（即重复报文） */
function markSeen(id: string): boolean {
  if (seenMids.has(id)) return false
  if (midQueue.length >= DEDUPE_CAP) {
    const oldest = midQueue.shift()
    if (oldest !== undefined) seenMids.delete(oldest)
  }
  midQueue.push(id)
  seenMids.add(id)
  return true
}

/** 时间戳纠偏：缺失或漂移过大 → 用本地接收时间顶替并打标 */
function fixTs(raw: unknown, recvTs: number): { ts: number; corrected: boolean } {
  const ts = num(raw)
  if (ts === undefined) return { ts: recvTs, corrected: true }
  if (Math.abs(ts - recvTs) > MAX_TS_DRIFT_MS) return { ts: recvTs, corrected: true }
  return { ts, corrected: false }
}
```

两个细节都有讲究：去重集合用 `Set + 队列` 做**环形淘汰**——只记最近 500 个 id，长会话内存恒定；漂移钳制设了 5 分钟容忍带——90 秒的小偏移在容忍范围内**保留设备原值**，只有超过阈值才判定"设备时钟坏了"并钳制为接收时刻。宁可容忍小漂移，也不粗暴改写可信数据。

再看 `decodeTelemetry` 主体，注意它同时消化单包与批量信封：

```ts
// 文件: demo/src/services/mqtt/codec.ts（节选）
export function decodeTelemetry(payload: unknown, recvTs: number): DecodeResult<TelemetryPoint[]> {
  codecStats.received++
  const parsed = parseJson(text(payload))
  if (!parsed.ok) {
    codecStats.dropped++
    return parsed
  }
  const obj = parsed.value

  // 去重：以报文 mid 为准；缺 mid 的报文无法去重，仍照常处理
  const id = typeof obj.mid === 'string' ? obj.mid : null
  if (id && !markSeen(id)) {
    codecStats.duplicates++
    codecStats.dropped++
    return { ok: false, reason: '重复报文' }
  }

  // 批量信封 → 展开为多个遥测点
  if (Array.isArray(obj.samples)) {
    const points: TelemetryPoint[] = []
    for (const s of obj.samples) {
      if (!s || typeof s !== 'object' || Array.isArray(s)) continue
      const p = normalizeSample(s as Record<string, unknown>, recvTs)
      if (p) points.push(p)
    }
    if (points.length === 0) {
      codecStats.dropped++
      return { ok: false, reason: '批量信封内无有效样本' }
    }
    codecStats.decoded++
    return { ok: true, value: points }
  }

  // 单包路径：同样走 normalizeSample，见源码
  // …
}
```

设计上最值得学的是 **Result 风格返回值**：`DecodeResult<T> = { ok: true; value: T } | { ok: false; reason: string }`。坏报文是常态而非异常（设备固件 bug、网络截断都会发生），用返回值表达失败，调用方 `if (r.ok)` 一行分发，不抛异常、不写 try/catch 链。`normalizeSample` 逐字段清洗——`num()` 把字符串数字兜底转换、非有限数一律剔除，**保证 NaN 永远流不进 UI**；没有 `on` 字段的传感器样本与有 `on` 的插座样本被收敛成同一个 `TelemetryPoint`（可选字段差异，见 3.2 章的契约先行）。

所有工序都会打点到模块级单例 `codecStats`（received/decoded/dropped/duplicates/corrected），顶栏的连接指示器直接消费它：

```vue
<!-- 文件: demo/src/components/ConnectionIndicator.vue（节选） -->
<template>
  <div class="conn" :title="conn.detail || conn.state">
    <div class="conn-row">
      <span class="conn-dot" :class="cls" />
      <span class="conn-label">{{ label }}</span>
    </div>
    <div class="conn-sub">解析 {{ codecStats.decoded }} · 丢弃 {{ codecStats.dropped }}</div>
  </div>
</template>
```

"解析 N · 丢弃 N"这行小字，就是整条流水线的体检表——联调时它是你判断"数据到底进没进来"的第一现场。

你会在控制台看到成对出现的输出：

```text
[route] iot/gh01/gh01-001/up/telemetry 95 bytes
[telemetry→store] gh01-001 1 点
[route] iot/gh01/gh01-002/up/telemetry 305 bytes
[telemetry→store] gh01-002 4 点        ← 低功耗批量信封展开为 4 个点
```

再和终端 1 的 broker 日志三方对照：

```text
[broker] dev-gh01-001 → iot/gh01/gh01-001/up/telemetry (95B, qos0)
```

字节数一致、deviceId 一致、点数与信封结构对得上——三个观察点串成完整证据链。若 `[route]` 有而 `[telemetry→store]` 无，问题必在解码层（看 `codecStats.dropped` 与 `reason`）；若 broker 日志都没有，问题在设备侧或连接层。**分段日志 + 计数器，比全靠断点单步快得多**——因为消息流是持续的，断点会阻塞后续报文，日志不会。

## 运行与验证

- [ ] **详情曲线滚动**：点击"育苗棚 A1"进入详情，温度/湿度曲线每 4~8 秒长出一个新点，视图持续向右推进；`windowCap=120` 意味着约 10 分钟后最早的数据开始被裁掉，曲线呈"滚动窗口"形态。
- [ ] **低功耗批量观察**：进入"育苗棚 A2（低功耗）"，曲线每 15 秒一次性跳 4 个点——批量信封在图表上的直观体现；它的样本时间戳带 90 秒偏移，但仍在 5 分钟容忍带内，因此保留原值（`corrected` 不打标）。
- [ ] **解码统计增长**：顶栏"解析 N · 丢弃 N"持续增长；丢弃计数会**偶发 +1**——那是模拟器 6% 概率的重复报文被去重拦下（duplicates 计入 dropped）。
- [ ] **server 日志对照**：终端 1 每条上报都有 `[broker] dev-xxx → iot/.../up/telemetry (xxB, qos0)`；浏览器侧"解析"计数与 broker 日志条数增长节奏一致（注意：`up/status`、`up/event` 也计入 received，短暂对不齐属正常）。
- [ ] **不认识的主题静默忽略**（可选实验）：从终端 1 无法直接发，可临时在模拟器 `reportSensor` 里加一行 `client.publish('foo/bar', 'x')`，重启后前端控制台与界面毫无反应——`parseTopic` 返回 null 被静默忽略，验证完删掉。

## 最佳实践与常见坑

**坑 1：Topic 解析不做边界防御，一个野主题打崩整条流水线**

- 现象：自己写的解析用 `topic.split('/')` 取第 4 段，某天 Broker 上出现了别的应用发布的 `$SYS/broker/uptime` 或层级不全的主题，控制台抛 `Cannot read properties of undefined`，此后所有消息都不再处理。
- 原因：字符串解析默认"世界只有我的主题"。真实环境里 Broker 是共享基础设施，$SYS 系统主题、其他业务主题、畸形主题都会到达订阅端（取决于订阅通配符与 Broker 权限）。
- 解法：学 demo 的三重防御——**白名单正则**（层级数、取值集合全部锁定，`TOPIC_RE`）、**null 语义**（解析失败返回 null，调用方静默忽略而非抛错）、**switch default 分支**（即使 kind 意外也不处理）。解析器必须假设输入是敌意字符串。

**坑 2：滑窗只 push 不裁剪，长会话内存爆掉**

- 现象：页面挂一下午，浏览器标签内存从 100MB 涨到 1GB+，曲线渲染肉眼可见地卡。
- 原因：每条遥测都 `window.push(p)` 却没有上限。8 台设备秒级上报，一小时就是上万条点位，ECharts 还要把它们全部画出来。
- 解法：**滑窗必须有上限**。demo 用 `CONFIG.windowCap = 120`，入库后 `splice(0, length - cap)` 一次性裁掉超限的最旧数据（一次内存操作，比循环 `shift()` 逐条删高效）。同时提醒：去重集合（`seenMids`）这类"只增不减"的结构同样要设环形淘汰上限（`DEDUPE_CAP = 500`）。

**坑 3：在 message 回调里直接深层 setState，引发渲染风暴**

- 现象：实现"来一条画一条"后，8 台设备同时上报时页面明显掉帧，Vue DevTools 里图表组件每秒重渲染七八次。
- 原因：`message` 事件回调里直接改深层响应式对象（如逐条 `window.push` 后立刻读它渲染图表），每条消息都触发一次依赖它的组件重渲染；图表每秒 `setOption` N 次，ECharts 布局计算成为瓶颈。消息频率越高越卡，且卡顿随设备数线性放大。
- 解法：**消息侧与渲染侧解耦**。消息侧只负责快速入库（demo 的 `ingestTelemetry` 只做 push/裁剪/赋值，微秒级）；渲染侧按固定节奏批量取数——图表 800ms `setInterval` 从滑窗快照取数一次，消息再密集帧率也不变。次要展示（卡片"上报于 x 秒前"）同理：5 秒刷一次 `now`，而不是每条消息都刷。原则：**高频写入用宽容的消费者，别让渲染层贴着消息节奏跑**。

**坑 4：去重键选错，去重形同虚设**

- 现象：自己实现去重时用 `JSON.stringify(payload)` 当键，出现两个问题：偶尔把内容相同但 `mid` 不同的合法报文误杀；或对象序列化顺序不稳导致重复报文漏网。
- 原因：报文身份应该由**发送方显式声明的唯一标识**（契约中的 `mid`）决定，而不是 payload 内容指纹。内容指纹在"重发同值新样本"与"重发同报文"之间无法区分。
- 解法：契约先行——要求设备每条报文带 `mid`，前端以 `mid` 为去重键（demo 即如此）；缺 `mid` 的报文按策略放行或丢弃，但要在文档里写清楚。同时留意 QoS 1 的重复发生在传输层，唯一可靠的去重键只能是业务 id。
