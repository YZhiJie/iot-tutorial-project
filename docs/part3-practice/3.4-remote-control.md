## 3.4.1 为什么「发布成功」不等于「执行成功」

监控台里一个按钮背后是这样的链路：

```text
浏览器 ──publish──▶ Broker ──▶ 设备（TCP 长连接）──▶ 固件执行 ──▶ 回执
```

`mqtt.js` 的发布操作返回成功，只代表 **Broker 收下了这条报文**，之后每个环节都可能掉链子：

- **设备不在线**：报文只会留在 Broker（clean 会话下甚至直接丢弃），设备永远不会执行；
- **设备拒收**：固件校验参数不合法（例如温度阈值超出允许范围），明确拒绝执行；
- **执行失败**：继电器卡死、固件崩溃，设备收到了但没做成。

对用户来说这三种结局完全不同，但 MQTT 协议层对此一无所知。所以必须在**业务契约层**补一个「指令回执」：设备执行完（或拒绝）后，向 `down/command_reply` 主题回一条带请求 id 的报文，前端拿它来闭环。这正是 Topic 契约里 `down/command` 与 `down/command_reply` 成对出现的原因。

一句话：**发布是「寄出」，回执才是「签收」。**

## 3.4.2 RPC over MQTT：publishCommand 逐行拆解

`IotGateway.publishCommand` 是指令下发的唯一入口，返回值是三态判别联合：

```ts
// 文件: demo/src/types/iot.ts
/** 指令下发结果（前端视角：成功 / 拒绝 / 超时 三态） */
export type CommandOutcome =
  | { status: 'ok'; message: string }
  | { status: 'rejected'; message: string }
  | { status: 'timeout' }
```

> 运行方式：类型定义已随 demo 项目提供，`pnpm dev` 启动后自动生效，无需单独运行。

注意两个建模决定：**不是布尔值**（要区分「没做成」和「没回音」），**Promise 永不 reject**（原因见下文）。

### 第一步：生成请求 id

```ts
// 文件: demo/src/services/mqtt/index.ts
publishCommand(
  deviceId: string,
  productId: string,
  action: CommandAction,
  params?: Record<string, unknown>,
): Promise<CommandOutcome> {
  const id = uuid()
  const msg: CommandMessage = { id, action, params, issuedAt: Date.now() }
  // ……见下一段：登记 pending + QoS 1 发布 + 超时兜底
}
```

> 运行方式：该文件已随 demo 提供；`pnpm dev` 后进入设备详情页点击控制按钮即可触发。

id 由 `utils/uuid.ts` 生成，这里藏着一个真实项目踩过的坑：

```ts
// 文件: demo/src/utils/uuid.ts
export function uuid(): string {
  if (typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function') {
    return crypto.randomUUID()
  }
  return `${Date.now().toString(36)}_${Math.random().toString(36).slice(2, 10)}`
}
```

> 运行方式：该文件已随 demo 提供，前端启动后自动生效。

`crypto.randomUUID()` 只在**安全上下文**（https 或 localhost）可用。用 `http://192.168.x.x` 这类局域网 IP 在手机上联调时它并不存在，直接调用会抛错。所以这里做了降级：时间戳 + 随机串拼接。对「一次指令一个 id」的场景，碰撞概率足够低，不必引入完整 UUID v4 实现。

### 第二步：登记 pending、QoS 1 发布、8 秒超时兜底

```ts
// 文件: demo/src/services/mqtt/index.ts
return new Promise<CommandOutcome>((resolve) => {
  const timer = setTimeout(() => {
    this.pending.delete(id)
    resolve({ status: 'timeout' })
  }, CONFIG.commandTimeoutMs) // 8000ms，见 src/config.ts
  this.pending.set(id, { resolve, timer })
  try {
    // QoS 1：指令必须送达（至少先到一次），遥测才用 QoS 0
    this.conn.publish(commandTopic(productId, deviceId), JSON.stringify(msg), 1)
  } catch (err) {
    clearTimeout(timer)
    this.pending.delete(id)
    resolve({ status: 'rejected', message: (err as Error).message })
  }
})
```

> 运行方式：该文件已随 demo 提供，无需单独运行。

四个要点：

1. **先登记 pending，再发布**。顺序反了的话，回执可能在 `pending.set` 之前到达——本地 Broker 延迟极低，这不是杞人忧天。
2. **指令用 QoS 1，遥测用 QoS 0**。指令低频高价值，必须「至少送达一次」；遥测高频且容忍丢失，降 QoS 省资源。
3. **超时兜底是 resolve，不是 reject**。8 秒到点后删掉 pending 记录并 `resolve({ status: 'timeout' })`。为什么不 reject？因为超时是**预期中的业务结果**而不是异常：调用方只需要把日志状态改成「超时」；用 try/catch 包住每个按钮只会让代码难看，漏写 catch 还会污染全局 `unhandledrejection`。三态全部走 resolve，调用方一个分支结构就写完。
4. **本地发布抛错也收口为 rejected**。`MqttConnection.publish` 在未连接时会 throw（`MQTT 未连接，无法发布`），catch 后同样 resolve——保证调用方拿到的 Promise **一定会 settle**，不存在悬挂。

### 第三步：settle——用 id 把回执接回 Promise

```ts
// 文件: demo/src/services/mqtt/index.ts
/** 用请求 id 把回执接回对应的 Promise */
private settle(reply: CommandReply): void {
  const p = this.pending.get(reply.id)
  if (!p) return // 超时后才姗姗来迟的回执：静默忽略
  clearTimeout(p.timer)
  this.pending.delete(reply.id)
  p.resolve(
    reply.ok
      ? { status: 'ok', message: reply.message }
      : { status: 'rejected', message: reply.message },
  )
}
```

> 运行方式：该文件已随 demo 提供，无需单独运行。

回执经 `route()` 的 `command_reply` 分支进入 `settle`，三个关键设计：

- **以 id 关联，而不是以主题关联**。同一设备的所有指令走同一个主题，主题匹配无法区分「哪次点击」；只有请求 id 能把回执精确路由给对应的 Promise。
- **迟到回执静默忽略**。8 秒超时后 pending 里已无记录，姗姗来迟的回执 `if (!p) return` 直接丢弃。要不要给用户补一条「指令实际已执行」的提示？可以，但需要新的通知通道；本 demo 保持简单，仅在 `useIot` 的 `onCommandReply` 里留了一条 console 日志供联调。
- **`stop()` 按超时语义收口**。应用卸载时把全部未完成指令 resolve 为 timeout，避免组件里的 `await` 永远悬挂。

### 拒绝路径：设备怎么「说不」

`rejected` 不是摆设，模拟器里有真实的拒绝分支——`setThreshold` 的参数校验（3.4.4 详述）：阈值不在 [20, 60] 区间时，设备回 `{ id, ok: false, message: '阈值超出允许范围 [20, 60]' }`，前端日志立刻变红「被拒绝」。你将在「运行与验证」里亲手触发它。

## 3.4.3 ControlPanel：把三态结果变成用户看得懂的日志

组件的核心是三条交互约束：**设备离线或连接未就绪时禁用按钮**；**每次指令记录一条日志，状态机 pending → ok / rejected / timeout**；**日志超过 20 条淘汰最旧**。

```ts
// 文件: demo/src/components/ControlPanel.vue
const canControl = computed(() => Boolean(entry.value?.online) && conn.isConnected)

type LogStatus = 'pending' | 'ok' | 'rejected' | 'timeout'
interface CommandLog {
  id: string
  label: string
  status: LogStatus
  message: string
  sentAt: number
}
const logs = ref<CommandLog[]>([])

async function send(label: string, action: CommandAction, params?: Record<string, unknown>): Promise<void> {
  const e = entry.value
  if (!e?.profile || !canControl.value) return
  const id = uuid()
  logs.value.unshift({ id, label, status: 'pending', message: '等待设备回执…', sentAt: Date.now() })
  if (logs.value.length > 20) logs.value.pop()

  const outcome = await getGateway().publishCommand(props.deviceId, e.profile.productId, action, params)

  const log = logs.value.find((l) => l.id === id)
  if (!log) return
  log.status = outcome.status === 'ok' ? 'ok' : outcome.status
  log.message =
    outcome.status === 'timeout'
      ? `${CONFIG.commandTimeoutMs / 1000}s 内未收到设备回执`
      : outcome.message || outcome.status
}
```

> 运行方式：该文件已随 demo 提供；`pnpm dev` 后进入任一设备详情页即可看到「远程控制」面板。

几个细节值得拆开看：

- **禁用条件是「设备在线 && MQTT 已连接」的与**。只有其一会漏：MQTT 连着但设备离线，指令是没人收的「假指令」；设备在线但浏览器正处重连中，指令也出不了门。模板里所有按钮绑定 `:disabled="!canControl"`，面板顶部同时给出一行提示「设备离线或连接未就绪，指令已禁用」。
- **日志状态机由 `CommandOutcome` 直接驱动**。pending 是本地乐观状态；await 返回后用 `outcome.status` 覆盖。timeout 单独拼一条更友好的文案（「8s 内未收到设备回执」），ok / rejected 直接展示设备返回的 `message`。
- **日志条目自己带本地 id**。回执是按指令 id 关联的，但组件内部找日志行用的是自己生成的 `uuid()`——此时指令还没出门，本地 id 一定唯一且查得到。
- **20 条上限**与告警 store 的 200 条上限是同一个思想：长会话只保留最近 N 条，防内存缓慢增长。

**一个值得讨论的缺口：pending 期间按钮并没有禁用。** 你可以连点三次「打开插座」，产生三条 pending 日志且最终都可能成功。这对开关这种**幂等指令**无害（执行三次结果一样），但对 `reboot` 意味着设备可能被连续重启三次。生产系统的常见做法：

1. send 期间按 action 维度记录 in-flight 状态并禁用对应按钮（最简单，本 demo 的推荐改造）；
2. 指令层去重：同设备同 action 且 params 相同的 pending 指令复用同一个 Promise；
3. 设备侧幂等键：把请求 id 传给固件，重复 id 直接重放上次的回执。

方案 1 前端自洽；方案 3 最彻底但要动固件——按团队边界选。

## 3.4.4 模拟器端：handleCommand 与三种指令剧本

设备端订阅 `down/command`，收到后统一走 `handleCommand`，回执带请求 id 发回 `down/command_reply`：

```js
// 文件: demo/server/simulator.mjs
function handleCommand(client, state, msg) {
  const { id, action, params } = msg ?? {}
  if (typeof id !== 'string') return
  const reply = (ok, message) =>
    publish(client, `${state.base}/down/command_reply`, { id, ok, message }, { qos: 1 })

  switch (action) {
    case 'switch': {
      state.on = Boolean(params?.on)
      setTimeout(() => reply(true, `开关已${state.on ? '打开' : '关闭'}`), 300)
      break
    }
    case 'setThreshold': {
      const v = Number(params?.tempMax)
      if (!Number.isFinite(v) || v < 20 || v > 60) {
        reply(false, '阈值超出允许范围 [20, 60]')
        break
      }
      state.threshold = v
      setTimeout(() => reply(true, `温度阈值已更新为 ${v}℃`), 200)
      break
    }
    case 'reboot': {
      // 重启剧本：先下线（retained），2.5s 后带完整档案重新上线，再补发回执
      publish(client, `${base0(state)}/up/status`, { online: false, reason: 'rebooting' }, { qos: 1, retain: true })
      setTimeout(() => {
        // ……此处省略：重新发布 retained 的完整在线档案（与上线注册时报文一致）
        reply(true, '设备已完成重启')
      }, 2500)
      break
    }
    default:
      reply(false, `不支持指令: ${action}`)
  }
}
```

> 运行方式：随 `pnpm server` 自动启动；也可在 demo 目录单独执行 `pnpm devices` 只跑设备模拟器。

三种剧本刻意拉开了「执行耗时」的梯度，正好覆盖三态的观察场景：

- **switch：立即执行**（300ms 模拟继电器动作）。状态翻转后，功率遥测跟着变：开 → 约 1150~1350W，关 → 0W。
- **setThreshold：先校验再生效**。非法值**同步回执拒绝**（前端立刻拿到 rejected）；合法值写入 `state.threshold` 后回执成功——此后 TEMP_HIGH 事件的文案会带上新阈值。
- **reboot：最慢也最特殊**。先发布 retained 的离线状态（前端卡片立刻变灰），2.5 秒后重新发布完整在线档案，**然后才补发成功回执**——模拟真实固件「重启完成后才能上报」的时序。观察曲线：断流 → 档案重新注册 → 恢复上报。

依次验证三条链路：

1. **开关插座**：进入 pl01-001 详情 → 点「关闭插座」→ 约 0.3s 后日志变绿「成功 · 开关已关闭」→ 下一个上报周期功率曲线落到 0W；再点「打开插座」→ 回执「开关已打开」→ 功率回到 1200W 附近。

## 最佳实践与常见坑

**坑 1：没有超时兜底，按钮永远 loading。**
现象：偶发场景下指令日志停在「执行中」，永远不落定。
原因：只在「回执到达」这一条路径上 resolve；设备掉线或网络抖动时回执永远不来，Promise 悬挂，UI 状态无人更新。
解法：`setTimeout` 兜底 `resolve({ status: 'timeout' })`（本 demo 为 8s）；同时保证 `stop()` 时清空全部 pending，不留悬挂。

**坑 2：用主题匹配而不是 id 关联回执。**
现象：连续下发两条指令，第二条的回执「成功」显示到了第一条日志上，或干脆丢失。
原因：同一设备的 `down/command_reply` 主题唯一，按主题分发无法区分是哪一次请求；并发时序一乱就串线。
解法：请求携带唯一 id，网关维护 `pending: Map<id, { resolve, timer }>`，回执按 `reply.id` 精确 settle。

**坑 3：只判 timeout，不处理 rejected。**
现象：设备明明回了「参数非法」，UI 却一律显示超时，运维误判为网络故障，把锅甩给联调。
原因：把 `CommandOutcome` 当两态处理，`rejected` 分支被吞掉。
解法：UI 分支覆盖全部三态；rejected 时原样展示设备返回的 `message`——那是设备视角最准确的失败原因。

**坑 4：在非 localhost 的 http 环境直接用 `crypto.randomUUID()`。**
现象：用局域网 IP 打开页面，点控制按钮直接抛 `randomUUID is not a function`。
原因：`randomUUID` 仅在安全上下文（https / localhost）可用。
解法：参考 `utils/uuid.ts` 的降级写法；或整体切 https。

## 实操任务

**为系统新增 `setReportInterval` 指令：前端下发上报间隔，模拟器按新间隔上报。**

契约：`down/command` 载荷 `{ id, action: 'setReportInterval', params: { intervalSec }, issuedAt }`，合法范围 3~60 秒；回执 `{ id, ok, message }`。

前端侧（3 步）：

1. `src/types/iot.ts`：`CommandAction` 联合类型追加 `'setReportInterval'`——TypeScript 会立刻指出哪些分支需要补全；
2. `src/components/ControlPanel.vue`：传感器（非插座）分支加一个秒数输入框与按钮，调用 `send('上报间隔', 'setReportInterval', { intervalSec: n })`；
3. **无需改动 `IotGateway`**——`publishCommand` 对 action 无感知，这正是 RPC 封装的价值。

模拟器侧（2 步）：

1. `handleCommand` 增加 `case 'setReportInterval'`：校验 `intervalSec` 在 [3, 60]，非法值同步 `reply(false, ...)`；
2. 合法值存入 `state.reportIntervalSec`。当前传感器循环节奏由 `jitterLoop(4000, 8000, ...)` 写死，最省事的改法：让循环节奏读取 `state.reportIntervalSec * 1000`；或在收到指令后先调用 `state.stops` 里存的停止函数停掉旧循环，再按新间隔重启循环。

> 运行方式：两端改完重启 `pnpm server` 与 `pnpm dev`，下发 `intervalSec: 10` 后观察详情页「上报于 x 秒前」的刷新节奏与曲线点密度变化。
